A wrong answer on test 7 says nothing about why. Two tools turn that
doubt into a concrete input: Stress finds a small case where your
solution and an obviously correct one disagree, and Trace shows every
step of a run.

## A brute force in the same file

Write the solution, then the slow, obviously correct version below it
as `@alt(program)`. It reads the same input, already read for it, and
prints its own answer. `cpl build` strips it from the C++ you submit.

Here the fast version claims the best profit is always between two
neighbours. Press **Stress**:

```cp run input="3\n1 3 6\n"
let n: 1..=8 = read()
let a: [0..n]1..=20 = read()
var best = 0
for i in 0..n:
    if i > 0 and a[i] > a[i - 1]: best max= a[i] - a[i - 1]
print(best)
@alt(program)
fn slow():
    var best = 0
    for i in 0..n:
        for j in i + 1..n:
            best max= a[j] - a[i]
    print(best)
```

Stress makes random inputs from the types (`n: 1..=8`, values
`1..=20`), so no generator is needed. On the first disagreement it
shrinks the input to the smallest one that still fails, and shows both
answers, here three numbers where the best pair is not adjacent. The
sample passes; the idea is wrong.

Small ranges in the types are what make the cases small. Check with
`n: 1..=8`, then put the statement's limits back.

## The fix, checked

Keep the smallest value so far, and the best profit is the best
`a[i] - low`:

```cp run input="3\n1 3 6\n"
let n: 1..=8 = read()
let a: [0..n]1..=20 = read()
var best = 0
var low = a[0]
for x in a:
    best max= x - low
    low min= x
print(best)
@alt(program)
fn slow():
    var best = 0
    for i in 0..n:
        for j in i + 1..n:
            best max= a[j] - a[i]
    print(best)
```

Stress now reports that every random case agrees.

## Trace

**Trace** runs the program and records every step. The viewer opens in
a new tab, where you step backward and forward through the run and
see arrays, grids and tables change. It is the quickest way to see
where a loop first does something you did not expect.

On your machine the same tools are `cpl stress file.cp` and
`cpl run file.cp --trace`; the [stress guide](/docs/guides/stress)
covers custom generators (`@gen`) and checkers for problems with
several right answers (`@check`).
