# cf2183h — minimum total cost of k subsequences

Sorted, an optimal partition uses contiguous groups. The first group always
takes the prefix `0..st` (each of those elements lowers its cost), and past
it the segment cost `(P_i - P_j)(i - j)` is Monge, so the optimum `f(k)` is
convex in `k`. Aliens trick: charge each group a penalty, find the least
penalty whose optimum takes at most `k` groups, and read `f(k)` off the line
through that optimum. Each penalized problem is a Monge shortest path. The
port calls the DP-and-search lane's `std.dp.aliens` and `std.dp.monge_path`
(online LARSCH, O(n), the original's algorithm). The dream is the same two calls with the node list,
tie-break and group count owned by the library (`spec/lib/rationale/dp.md`).

## The Aliens tie-break, node list and group count are by hand (owned by DP and search area lane)

- **Where:** port lines 19-25: `let w = I128(n + 1)`, the node map
  `cut(p)` onto `0, st, ..., n`, `monge_path(n - st + 2, (p, q) => (cost(..) + pen) * w + 1)`,
  a walk of `prev` to count groups, and `(path.val.last! - groups) / w`;
  lines 27-28, the slope range `I128(0)..=1 - fewest`.
- **What felt wrong:** routed as asked, the lane landed
  `std.dp.monge_path(n, w) -> (val, prev)` and made `aliens` generic over
  the slope type, so the candidate deque, the slope search and the line
  interpolation are gone, and `monge_path` is now online LARSCH, so the
  k = n/2 max input takes **0.84 s** against **0.99 s** for the
  original (it was 3.63 s with the O(n log n) deque). Two gaps remain.
  (1) Shape: the path runs over `0..n`, not
  the node list `0, st, ..., n`, so the port remaps nodes, and it returns
  `prev` rather than the edge count, so the port walks the path to count
  groups. (2) `aliens` needs `solve` to report the fewest groups among
  ties, which the contestant gets by scaling every edge by `n + 1` and
  adding 1, then dividing back out: a correct but unguessable trick, and
  forgetting it is a wrong answer only when the optimum ties. The slope
  range is also the contestant's to bound (`1 - fewest`).
- **Goal it hurts:** express, performance, hard to get wrong.
- **Ideal code** (dream line 14):
  ```
  print(aliens(k, solve: pen => monge_path([0] + (st..=n), cost: (j, i) => cost(j, i) + pen)))
  ```
- **General fix:** in `spec/lib/rationale/dp.md`, make `monge_path` take a node list, and report the
  path's edge count (breaking ties toward fewer edges) alongside `prev`;
  let `aliens` infer its slope range from the value type.
- **Severity:** high
- **Dream:** `proto/ports/ecnerwala/dream/cf2183h.cp` line 14.

## `Range<I128>.len` wraps silently (owned by sequences area lane)

- **Where:** port line 28, `aliens(k, I128(0)..=1 - fewest, ...)`, whose
  `bsearch_first` runs over a slope range about 4e19 wide.
- **What felt wrong:** this used to fail with `expected I128, found I128`.
  Main then lowered `Range<I128>` and fixed `bsearch_first` over wide
  ranges (`crates/cpl-cli/tests/programs/bsearch_i128.cp`), so the search
  (now inside `aliens`) agrees with the original on both max inputs. But `len`
  on the same range still wraps with no trap:
  `print((I128(-4e10) * I128(1e9)..=I128(0)).len)` prints
  `3106511852580896769` (4e19 mod 2^64). Before the bsearch fix the port
  checked, passed `gate.sh cf2183h 150`, and printed a wrong answer on the
  k = n/2 max input for exactly this reason. This wave narrows the
  leftover unsupported-range diagnostic to `U64` (test in
  `crates/cpl-cli/tests/cli.rs`).
- **Goal it hurts:** hard to get wrong (silent overflow).
- **Ideal code:** none in the dream; `aliens` (dream line 14) owns the
  search.
- **General fix:** give `Range<I>.len` type `I`, or trap when it narrows.
  The regression is the program above.
- **Severity:** high
- **Dream:** `proto/ports/ecnerwala/dream/cf2183h.cp` line 14.

## Wide values need `I128(...)` on literals and products (owned by core lane)

- **Where:** port line 13, `I128(pref.sum(j..i)) * (i - j)`; line 19,
  `I128(n + 1)`; line 28, `I128(0)` as the range end.
- **What felt wrong:** the product needs an explicit `I128` on one
  factor, and forgetting it is a silent overflow in release; the declared
  result type and the operand ranges (`pref` up to 2e14, lengths up to 2e5)
  already prove the product is wide.
- **Goal it hurts:** hard to get wrong (overflow), express.
- **Ideal code** (dream line 11):
  `fn cost(j: a.Cut, i: a.Cut) -> I128 = (pref[i] - pref[j]) * (i - j)`
- **General fix:** widen literals field-wise in tuple context, and evaluate
  an expression at its declared result width when operand ranges show the
  narrow form can overflow (or warn there).
- **Severity:** medium
- **Dream:** `proto/ports/ecnerwala/dream/cf2183h.cp` line 11.

## Prefix sums and the first-group cut are spelled by hand (owned by sequences area lane)

- **Where:** port line 11, `let pref = prefix(a)`, read through
  `pref.prefix(c)` and `pref.sum(j..i)` with plain `Int`s; line 12,
  `(0..n).first(c => pref.prefix(c) + a[c] * c > 0) ?? n`.
- **What felt wrong:** prefix sums are cuts of `a`, but `prefix` is
  read through methods over untyped `Int`s, so cuts and positions mix in
  `cost` and in `a[c] * c`. The `?? n` turns "every prefix element lowers
  its cost" into a sentinel. The obvious `[0] + scan(a, +)` is worse: it
  indexes cleanly but its stdlib body drags a 1.2 KB optional-position
  template into the emitted C++ (this port: 20,970 B with `scan` against
  19,491 B with `prefix`), enough to trip the scoreboard's +5% size gate.
- **Goal it hurts:** hard to get wrong (cut/position mix), express.
- **Ideal code** (dream lines 9-10):
  ```
  let pref = a.prefix_sums()                                       // [a.Cut]Int
  let st = a.cuts.find(c => c == n or pref[c] + a[c] * c > 0)!
  ```
- **General fix:** `xs.prefix_sums() -> [xs.Cut]T` and `xs.cuts` as a
  domain, so the zero cut and the last cut exist and are typed.
- **Severity:** medium
- **Dream:** `proto/ports/ecnerwala/dream/cf2183h.cp` lines 9-11.

## A stdlib module cannot use the prelude's `Deque` under `cpl run`
- **What felt wrong:** `std.dp` used `Deque` unimported; `cpl check` and
  `cpl test stdlib/dp.cp` passed, but every importing program failed with
  `E0204: Deque is not a type cpl run knows` (`E0501` on a generic fn).
  Fixed locally with `use std.deque.{Deque}`.
- **Goal it hurts:** 4 (doubt to evidence); coherence.
- **General fix:** lowering sees the same prelude as the checker. Owner: core.
- **Severity:** medium.
- **Dream:** none (stdlib-internal).

## What worked

- `read<[n]-1e9..=1e9>().sorted()`, `prefix(a).sum(j..i)` for segment
  sums, `(0..n).first(...)` for the cut, and
  the early `return print(...)` for the closed form read like the
  editorial.
- `std.dp.monge_path` replaced 17 lines of candidate deque, and
  `std.dp.aliens` over an `I128` slope range replaced the slope search and
  the line interpolation; both agree with the original on the max inputs.
- Nested `fn`s that capture now lower to plain lambdas (main's
  static-closure codegen): the emitted C++ has no `std::function`, so
  that friction is closed.
