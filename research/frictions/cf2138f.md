# cf2138f friction

Draw a ladder of triangles between two rails: each new point joins the current tips of
both rails, so the operation count is exactly `m` and is printed first. With `m` even the
rungs are `t / (m/2)` long and the far rail is a fixed offset of the near one. With `m`
odd the rungs are unit vectors along `t`; three opening points (a corner found by a
1/64 grid search, a start on the line, and the first rung) bridge from the segment
`P1 P2` onto that line. The original builds a vector of operations and prints it; the
port streams them.

## No floating-point vector, and operators cannot scale by a number
- **Where:** `struct V(x: F64, y: F64)` with its own `len`, `impl Add`, `impl Sub`, and
  `fn times(a: V, k: F64)`, `fn over(a: V, k: F64)`; every scaled point is
  `side + times(d, F64(i - 1))`.
- **What felt wrong:** `stdlib/geometry.cp` has `Pt` over `Int` only, so a float problem
  starts by writing a vector type. Operators are same-type traits, so
  `impl Mul for V: fn mul(a, k: F64)` is `error[E0302]: expected V, found F64` at the use;
  scaling is a named call and reads inside out. `over` exists separately from `times`
  because the original divides (`t / k`) and multiplying by `1.0 / k` changes the last bits
  (two of the first eight random cases differed until it divided).
- **Goal it hurts:** express, coherence (a user's vector gets `+` and `-` but not scaling).
- **Ideal code:**
  ```cp
  use geometry.{Vec}
  let d = t / F64(k)
  ladder(2, 1, 1, i => side + d * F64(i - 1), i => d * F64(i))
  ```
- **General fix:** a generic `Pt<T>` (or `Vec<F64>`) in `geometry` with `len`, `unit`,
  `dist`; operator traits with a right-hand type (`impl Mul<F64> for V`) so scalar
  products and quotients are operators in user code too.
- **Dream:** `dream/cf2138f.cp` lines 1, 8, 27 and 29-30.
- **Severity:** medium.
- **Status:** resolved (`std.geometry.Vec` provides `Add`/`Sub`/`Neg`/`Mul<F64>`/`Div<F64>`/`len`/`unit` after `ad1291e5`, so `cf2138f.cp` writes `t / F64(k)` and `d * F64(i)` directly).

## A first-match search over a grid needs a function, an early `return` and a fake fallback
- **Where:**
  ```cp
  fn side() -> V:
      for x in -64..=64:
          for y in -64..=64:
              let c = V(F64(x) / 64.0, F64(y) / 64.0)
              ...: return c
      p1
  ```
- **What felt wrong:** "the first grid point that fits" is one expression. Ranges have
  `find`, but there is no product of ranges to call it on; the two-clause comprehension
  `[c for x in -64..=64 for y in -64..=64 if ...].first!` reads right but is eager: it
  tests all 16641 points (five square roots each) for every odd test, where the answer
  is usually found in the first few hundred, and up to 33333 odd tests fit in the
  budget. There is no `unreachable()` (`E0201`), so the loop version ends with a made-up
  value `p1` the program never means.
- **Goal it hurts:** express, hard-to-get-wrong (a sentinel that silently becomes an answer
  if the search ever fails).
- **Ideal code:**
  ```cp
  let s = (-64..=64).pairs(-64..=64).map((x, y) => V(x / 64, y / 64))
      .find(c => [p1, p2, t0, t1, start].all(e => fits(c, e)))!
  ```
- **General fix:** a lazy product of ranges (or a lazy comprehension) that `find` can
  stop early on, returning `?T`; `!` already traps on `none`, which is the "unreachable"
  the program means. Helps every brute-force search for a witness.
- **Dream:** `dream/cf2138f.cp` lines 32-34.
- **Severity:** medium.

## `List` has `find` but no `all`
- **Where:** the conjunction of five `fits(c, ...)` checks above.
- **What felt wrong:** `xs.find(p)` works, and segment trees have `.all` (meaning the
  whole fold), but `[p1, p2, t0, t1, start].all(e => fits(c, e))` is `error[E0203]: a
  List<V> has no method all that cpl run knows` (the same for `List<Int>`), plus a bogus
  `expected V, found Int` on the lambda. The five checks are written out by name, split
  over two lines to fit the width.
- **Goal it hurts:** coherence (`find` without `all`, and `all` meaning a fold elsewhere),
  express.
- **Ideal code:** `[p1, p2, t0, t1, start].all(e => fits(c, e))`.
- **General fix:** `all`/`any` beside `find` on every sequence; the name clash with the
  segment trees' `.all` (whole fold) is worth resolving at the same time.
- **Dream:** `dream/cf2138f.cp` line 33.
- **Severity:** medium.
- **Status:** resolved (`List.all` is now supported; `cf2138f.cp` uses `[p1, p2, t0, t1, start].all(e => fits(c, e))`).

## Point identifiers are counted by hand
- **Where:** `var drawn = 2` and `fn draw(u, v, c) -> Int` that prints and returns the new id;
  the opening of the odd case is `draw(1, 2, s)`, `draw(2, a, start)`, `draw(a, b, t1)`.
- **What felt wrong:** the output names points by creation order; the program must keep
  a counter beside the print. It is local and correct, so this is minor.
- **Goal it hurts:** express.
- **Ideal code:** `var pts = [p1, p2]`, `pts.push(c)` returning the new index (1-based
  domain), print from the list.
- **General fix:** `push` returning the new element's index in the list's domain.
- **Dream:** `dream/cf2138f.cp` lines 13-16.
- **Severity:** low.
