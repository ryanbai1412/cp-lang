# cf2069f — Codeforces 2069 F (Graph Inclusion)

Ported: `proto/ports/ecnerwala/cf2069f.cp`. A contains B after adding the
fewest edges exactly when every B edge joins vertices A already connects,
so the answer is `components(A) - components(A + B)`. Offline dynamic
connectivity: each edge lives on a range of query times; recurse on halves
of the time range, apply the edges covering a half to two rollback DSUs,
pass the partial ones down, undo. O(q log q log n), the same algorithm as
the original.

## Offline "segment tree over time" is written by hand every time
- **Where:**
  ```cp
  fn solve(span: Range<T>, live: List<Edge>):
      let snap = (a.mark(), ab.mark())
      var rest: List<Edge> = []
      for e in live:
          if e.on.lo <= span.lo and span.hi <= e.on.hi: ...
          elif e.on.lo < span.hi and span.lo < e.on.hi: rest.push(e)
      ...
      a.undo_to(snap.0)
      ab.undo_to(snap.1)
  ```
- **What felt wrong:** the idea is "for each time t, the answer on the
  graph of edges alive at t", with rollback. The port spells out the
  recursion, the covers/overlaps tests, the per-level `List<Edge>` copy and
  the paired mark/undo of two DSUs; forgetting one `undo_to` is a silent
  wrong answer. The pattern is the standard one for offline deletions.
- **Goal it hurts:** express, hard-to-get-wrong.
- **Ideal code:**
  ```cp
  offline_over(T, edges, by: e => e.on, with: (a, ab)) (e) =>
      if e.in_a: a.unite(e.x, e.y)
      ab.unite(e.x, e.y)
  at t => ans[t] = a.components - ab.components
  ```
- **General fix:** a stdlib `offline_over(domain, items, by: range,
  with: rollbackable...)` that owns the recursion and undo, for any state
  implementing a `Rollback` interface (`mark`/`undo_to`), so `Dsu`, user
  structures and tuples of them all qualify. Helps every offline-deletion
  port (dynamic connectivity, dynamic bipartiteness, knapsack with removals).
- **Severity:** high.
- **Status:** fixed: `std.timetree.TimeTree.run` and `std.timetree.offline_over` walk the segment tree over time via zero-allocation `mark`/`apply`/`answer`/`undo` callbacks (1 mark per non-empty tree node, devirtualized to static calls in C++). `proto/ports/ecnerwala/cf2069f.cp` uses `tt.run(...)`, dropping the `marks` stack and `TimeStep` allocation (`1.31s -> 1.05s` median user, peak RSS `356 MB -> 146 MB` on `n = 400k, q = 400k`).
- **Dream:** `proto/ports/ecnerwala/dream/cf2069f.cp` lines 7-12

## Splitting a range at its midpoint is unguessable and failed at runtime
- **Where:** `let m = span.mid!`, `solve(span.lo..m.r, rest)`,
  `solve(m.r..span.hi, rest)`, plus `Edge(s.l..t.l, ...)` and `s.l..T.last.r`.
- **What felt wrong:** `Range<T>` bounds are cuts, `span.mid` is a position,
  and turning it back into a cut needs `.l` or `.r`. My first version split at
  `m.l`; for a two-element span that made an empty left half, and the
  interpreter trapped on `span.mid!` of the empty range. The fix (`m.r`) is
  right but nothing in the names says which one splits into two non-empty
  halves.
- **Goal it hurts:** hard-to-get-wrong (off-by-one), express.
- **Ideal code:** `let (left, right) = span.halves()` (both non-empty when
  `span.len >= 2`), and `t.l..t2.l` written as `t ..< t2` on positions.
- **General fix:** `Range.halves()` / `Range.split_at(pos)` in the stdlib,
  and a lint on `x.mid!.l` used as a split bound.
- **Severity:** high.
- **Dream:** `proto/ports/ecnerwala/dream/cf2069f.cp` lines 9 (`offline_over` owns the split)

## An unordered pair key is normalized by hand
- **Where:** `let key = (g, min(x, y), max(x, y))`
- **What felt wrong:** an undirected edge is a set of two vertices; the
  normalization is repeated wherever the key is built and forgetting it once
  splits one edge into two silently.
- **Goal it hurts:** hard-to-get-wrong.
- **Ideal code:** `let key = (g, {x, y})` with `{x, y}: Pair<V>` hashing and
  comparing as an unordered pair.
- **General fix:** an unordered `Pair<T>` (or `Edge<V>`) value type in the
  stdlib with `.a`, `.b` sorted, usable as a `Map` key.
- **Severity:** medium.
- **Dream:** `proto/ports/ecnerwala/dream/cf2069f.cp` lines 5, 10-11
