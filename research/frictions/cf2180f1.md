# cf2180f1 — Control Car (Easy Version)

The editorial idea: never fix the whole grid of arrows up front. Follow the
car and choose each corner only when the car first needs it. In a cell, the
bottom-left and top-right corners were already chosen by the cell it came
from (or are fresh at the border); the bottom-right corner is always fresh
and decides the move. So the state of a cell is two bits: is the floor shut
(bottom-left points right) and is the right wall shut (top-right points
down). A stop in `(i, j)` has chosen `2(i + j) + 3` corners, so its weight is
`4^-(2(i + j) + 3)`, and the car stops inside the `n x m` grid iff it stops at
some `i < n, j < m`. One `O(N M)` sweep tabulates every answer. The port says
this in a dozen lines, but the natural state layout was 3x slower, and the
two lines of modular constants are a silent wrong-answer trap.

## The natural "two more dimensions" layout is 3.2x slower, and 9.5x under the sanitizer
- **Where:** my first rolling draft (not committed):
  ```cp
  var ways: [J, Bool, Bool]Z = 0
  ...
  for floor in Bool:
      for wall in Bool: ways[j, floor, wall] += side[floor, wall]
  let open = ways[j, false, false]
  ```
  versus `cf2180f1.cp`, lines 19–21 and 30–36:
  ```cp
  type Ways = (open: Z, walled: Z, shut: Z, boxed: Z)
  var ways: [J]Ways = (0, 0, 0, 0)
  ...
  ways[j] = (6 * falls, 3 * falls, 2 * falls, falls)
  ```
- **What felt wrong:** "the DP gains a dimension" is the revision the
  language promises to keep local, and `[J, Bool, Bool]` is the first thing
  you write. It is the same algorithm and the same 16 bytes per column, but
  every access goes through the checked 3D index (`ways.ck(j, t15, t16)` in
  the emitted C++) and the Bool loops are not unrolled. Measured on the
  sample (which contains `5000 5000`), `g++ -O2`: 1198 ms with Bool axes vs
  370 ms with the named tuple; under the gate's `-O1` ASan/UBSan build 27.9 s
  vs 2.9 s. The gate's sanitizer limit is 20 s, so the natural layout fails
  the gate outright. I had to restructure the state into named fields to
  ship, and the next dimension (say, a third inherited corner) would mean
  renaming every field instead of adding an axis.
- **Goal it hurts:** performance (zero-cost domains), express (a revision
  that stops being local).
- **Ideal code:** `var ways: [J][Shut]Z` with `record Shut(floor: Bool, wall: Bool)`,
  and whole-row values `here = ways[j] + side` — `dream/cf2180f1.cp`,
  lines 9, 16 and 23–27.
- **General fix:** small fixed domains (`Bool`, enums, records of them) as
  inner axes lower to a fixed-size inline array whose index the compiler
  folds when the subscript is a literal, with the bounds check proved away;
  `[J][Shut]Z` is the same layout as the tuple. Element-wise `+` on such
  rows. Helps every bit-state DP (cf2183e's rolling rows, cf2178i's masks).
- **Severity:** high.

## `let q: Z = 1 / 4` is silently 0, and `4 ** e` disagrees between interpreter and C++
- **Where:** `cf2180f1.cp`, lines 23 and 39:
  ```cp
  let quarter = Z(1) / 4
  for x in q: print(Z(4) ** ((x.n + 1) * (x.m + 1)) * stopped[...])
  ```
- **What felt wrong:** `friction_lint.py` flags both `Z(1)` and `Z(4)` as
  stale "Mod literal wrapping", so I tried the unwrapped forms. Both are
  traps:
  ```cp
  let q: Z = 1 / 4          // Int division first: q == 0, no error
  let p: Z = 4 ** e         // Int power first
  ```
  With `e = 40` the interpreter stops with `R0001 integer overflow: 4 ** 40
  does not fit in an Int`, while the compiled C++ (`cpl::ipow(4, e)`) prints
  `0`; only the ASan build reports the signed overflow. So the expected type
  `Z` does not reach the literals, the obvious spelling is wrong, the lint
  steers you into it, and the two back ends disagree on the same program.
- **Goal it hurts:** hard-to-get-wrong (wrong modulus/arithmetic P0),
  submission (interpreter and C++ must agree).
- **Ideal code:** `(1 / 4) ** (2 * d + 3)` and `4 ** ((n + 1) * (m + 1))` in a
  `Z` context — `dream/cf2180f1.cp`, lines 18 and 31.
- **General fix:** bidirectional typing pushes the expected type into
  arithmetic on literals (`1 / 4 : Z` is the inverse of 4), or at least an
  error for `Int / Int` and `Int ** Int` coerced to `Mod`; the release C++
  must trap (or the type checker must reject) an `Int` overflow the
  interpreter traps. The lint rule must not fire where the wrap is needed.
- **Severity:** high.

## `Mod<P>` is stored in 64 bits: twice the original's memory
- **Where:** `cf2180f1.cp`, line 25: `var stopped: [I, J]Z = 0`.
- **What felt wrong:** the emitted `struct Mod_1000000007_2 { ll v; }` makes
  the 25M-cell answer table 200 MB (198656 KB peak) against the original's
  101120 KB with a 32-bit `modnum`. Values below `1e9 + 7` fit in 32 bits;
  the type knows it.
- **Goal it hurts:** performance (values take the fewest bytes their types
  allow).
- **Ideal code:** unchanged; `Z` is 4 bytes — `dream/cf2180f1.cp`, line 19.
- **General fix:** store `Mod<P>` in the narrowest unsigned type holding
  `P - 1`, widening only inside multiplication. Helps every table of
  residues (cf2183f's 25M-cell table too).
- **Severity:** medium.

## Two prefix sums written into the sweep, with a boundary branch and `(i - 1)!`
- **Where:** `cf2180f1.cp`, lines 28, 32 and 37:
  ```cp
  var run: Z = 0
  run += (walled + shut + 4 * (w.boxed + side.boxed)) * weight[i.to_idx + j.to_idx]
  stopped[i, j] = run + (if i == I.first: 0 else: stopped[(i - 1)!, j])
  ```
- **What felt wrong:** the answer is a 2D prefix sum of per-cell stops; I fused
  it into the DP by hand, with a row accumulator, a first-row branch and the
  domain-step unwrap `(i - 1)!` (flagged as a real gap by the friction lint).
  The per-cell weight crosses from two domains to an `Int` with `.to_idx`
  twice. Changing "inside the grid" to any other region means re-deriving
  the fused sum.
- **Goal it hurts:** express (one fact in one place), hard-to-get-wrong
  (boundary).
- **Ideal code:** `stops[i, j] = ... * weight[i + j]` and
  `let inside = stops.prefix_sums()` queried as `inside[..n, ..m]` —
  `dream/cf2180f1.cp`, lines 28, 30 and 31.
- **General fix:** a stdlib `prefix_sums` over multi-axis arrays returning a
  rectangle-sum view indexed by ranges, and position arithmetic `i + j : Int`
  for 0-based domains. The same view is cf2183f's whole inner loop.
- **Severity:** medium.

## Domains sized by the input need `max(x.n for x in q)!`
- **Where:** `cf2180f1.cp`, lines 12–15:
  ```cp
  let t = read(1..=10_000)
  let q: [0..t](n: 1..=5000, m: 1..=5000) = read()
  domain I = 0..max(x.n for x in q)!
  ```
- **What felt wrong:** sizing the table by the largest query is natural, but
  `max` over a nonempty list still returns an option (the `!` restates what
  `t >= 1` already proves), and a field projection over a list needs a
  generator. Answering queries offline also forces reading them all into a
  list before the loop, where a multitest block cannot be used.
- **Goal it hurts:** express.
- **Ideal code:** `domain I = 0..max(q.n)` — `dream/cf2180f1.cp`, lines 12–14.
- **General fix:** field projection on lists of records (`q.n`), and `max`
  returning a plain value when the range type proves nonemptiness.
- **Severity:** low.

## First-draft frictions: `else if` and iterating an enum
- **Where:** an earlier draft modelled each corner as `enum Dir: Up, Down,
  Left, Right` and enumerated the fresh corner.
- **What felt wrong:** `else if` is rejected (only `elif`), and `for d in Dir`
  is rejected because an enum type is not a domain, so the draft carried
  `let dirs = [Up, Down, Left, Right]`, a second copy of the enum's members
  that must be kept in sync by hand.
- **Goal it hurts:** express (unguessable; a fact written twice).
- **Ideal code:** the dream needs neither, but `for d in Dir` is what one
  writes — compare `dream/cf2180f1.cp`, line 9, where `Shut` is a domain.
- **General fix:** a payload-free enum is a domain (`Dir.all`, `[Dir]T`), and
  `else if` parses as `elif` (or a targeted error that says so).
- **Severity:** low.

## Measurements
- Contestant-written tokens: port 397 vs original 743 (`main`, lines
  281–350; the template is excluded) — 0.53x.
- Max input: the sample has `5000 5000`, which is the whole table
  (`g++ -O2`, three runs): port 370–380 ms, 198656 KB; original 710–730 ms,
  101120 KB. Output agreement: exact (`793450807` and the four small cases).

  gate needs `INTERP_TIMEOUT=900`.
- Emitted C++ size: 21587 bytes.
- Gate: `INTERP_TIMEOUT=900 gate.sh cf2180f1 150` passes (1 sample, 150 random
  cases).
