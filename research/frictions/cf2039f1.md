# cf2039f1 — Shohag Loves Counting (Easy Version)

The editorial: an array is good iff its values are distinct and, sorted,
have strictly growing suffix gcds; each such set has `2^(n−1)` good orders.
The port adds values from `m` down to 1: an open set (all values above `y`)
with gcd `g` takes `y` iff `gcd(y, g) < g`, doubling its weight. By Möbius
the weight landing on `h | y` is `Σ_{d | y/h} μ(d)·above[h·d]`, where
`above[x]` sums the open sets whose gcd `x` divides, less the sets already
at `h`. The sum of `m` is at most `10^5`, so each test sieves to its own `m`;
the original precomputes every `m <= 10^6` with a two-level harmonic DP.

## Sieve.divisors re-factors on every call
- **Where:** `port.cp`, lines 18 and 21: `numbers.divisors(y / h)`,
  `numbers.divisors(y)`, `numbers.divisors(h)`.
- **What felt wrong:** `Sieve.divisors(x)` now replaces the hand-built
  harmonic table, and the port reads like the dream, but each call runs
  `self.factor(x)` into a new `List` before yielding. At `m = 10^5` the port
  takes 0.41–0.43 s against 0.13 s for the previous hand-built
  `[m + 1]List<Int>` table (orig.cpp 1.14–1.23 s, so still well inside the
  bar). Caching the lists once (`divs[x] = numbers.divisors(x).collect()`)
  gives 0.25–0.36 s.
- **Goal it hurts:** performance (the obvious way is the fast way).
- **Ideal code:** `y.divisors` over a divisor domain, or
  `numbers.divisors(y)` at table speed.
- **General fix (stdlib/perf):** walk `spf` in the generator without
  materialising the factor list, or keep a lazily built divisor table on
  the `Sieve` (O(m log m) once, O(d(x)) per call).
- **Repro:** `let s = Sieve(100_000)` then
  `for y in 1..=100_000: for h in s.divisors(y): for d in s.divisors(h): t += d`
  is ~3x the same loops over a prebuilt `[m + 1]List<Int>` table.
- **Dream:** `dream.cp` lines 8, 12, 15.
- **Severity:** low.
- **Area:** math

## The divisor lattice has no index space
- **Where:** `port.cp`, lines 16, 18: `[1..=m]Z` arrays indexed by `Int`,
  `above[h * d]`, `divisors(y / h)`.
- **What felt wrong:** the values are `1..=m`, but a domain `G = 1..=m`
  does not allow `h * d` (`E0309: * can't be applied to G and Int`) or
  `y / h`, and `domain G = m.divisors` is `E0203` (no `Int.divisors`), so
  the port uses anonymous-range arrays `[1..=m]Z` (no unused slot 0,
  every index checked) with `Int` indices; `G(Int(h) * d)` at every use
  would bury the formula.
- **Goal it hurts:** hard to get wrong (wrong index space); express.
- **Ideal code:** `domain G = read(1..=1e5).divisors` with `h * d` and
  `y / h` defined when the result stays in `G`.
- **General fix (core/math):** a domain over `1..=m` with checked
  multiplication and exact division, or `D(x)` conversions short enough to
  write inline. Proposal only.
- **Dream:** `dream/cf2039f1.cp` lines 8, 10.
- **Severity:** medium.
- **Area:** core

## Scatter-add to every divisor is a loop
- **Where:** `port.cp`, line 21: `for d in numbers.divisors(h): above[d] += w`.
- **What felt wrong:** "add `w` at every divisor of `h`" is one statement in
  the editorial. `a[r] += w` works for a range `r`, but an index list is
  rejected (`E0301: this is indexed by Int, but the index is a List<Int>`), so the
  same operation has a statement form for contiguous indices only.
- **Goal it hurts:** express (one spelling per idea).
- **Ideal code:** `above[h.divisors] += w`.
- **General fix (core):** let compound assignment through an index take
  any sequence of indices, as it already takes a range. Proposed, not added.
- **Dream:** `dream/cf2039f1.cp` line 15.
- **Severity:** low.
- **Area:** core
