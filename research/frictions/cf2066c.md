# cf2066c — Bitwise Slides

The editorial's DP: after each step two of `P, Q, R` are equal (to some `x`)
and the third is the prefix xor, and of `ways[x]` only the entry for the
previous prefix changes, so the whole DP is one hash-map update per element.

## A map read with a default needs `.get(k) ?? 0` at every use
- **Where:** `cf2066c.cp`, line 9:
  ```cp
  ways[pre] = 3 * (ways.get(pre) ?? 0) + 2 * (ways.get(pre ^ x) ?? 0)
  ```
- **What felt wrong:** The DP is sparse over xor values, so `ways` is a map
  whose absent keys mean zero. `ways[k]` traps when absent, so every read
  spells the default again; the default is a fact about the map, repeated at
  each read, and the formula no longer reads like the recurrence
  `ways[pre] = 3 * ways[pre] + 2 * ways[pre ^ x]`. Turning a `[D]Z` DP into a
  map DP (the common revision when values are large) rewrites every read.
- **Goal it hurts:** express and revise (one fact in one place; array to map
  is supposed to be a local edit).
- **Ideal code:**
  ```cp
  var ways: HashMap<Int, Z> = [0: 1] default 0
  for x in a:
      ways[pre] = 3 * ways[pre] + 2 * ways[pre ^ x]
      pre ^= x
  print(sum(ways.values))
  ```
- **General fix (containers area):** a map declared with a default (`design/spec/26-containers.md`
  sparse maps; `Map.with_default(z)` or a `default` clause) whose reads return
  the default without inserting, so a dense array and a sparse map share the
  same indexing code. The same mechanism covers counters (`default 0`) and
  adjacency maps (`default []`).
- **Dream:** `dream/cf2066c.cp` lines 7 and 10: the default is declared once and every read is `ways[k]`.
- **Severity:** medium.
- **Area:** containers

## [Resolved] Maps have no `.values` / `.keys` views
- **Where:** `cf2066c.cp`, line 11: `print(ways.values.sum())` (was `print(sum(v for (_, v) in ways))`).
- **Resolution:** Added O(1) view getters `.keys` and `.values` on `Map` and `HashMap` (zero-allocation in `for` loops, comprehensions, and reductions; materializes `List<K>`/`List<V>` when kept as a value) with interpreter/C++ parity, and migrated `cf2066c` and `cf2150c`.
- **Goal it hurts:** express (guessable APIs).
- **Severity:** low.
- **Area:** containers

## A length read in place must be a half-open range, `[0..read(...)]`
- **Where:** `cf2066c.cp`, line 2: `let a: [0..read(1..=2e5)]1..=1e9 = read()`.
- **What felt wrong:** the statement gives "n, then n values"; `[read()]T`
  (a length, as `read<[n]T>()` already accepts) is rejected with `E0203`
  "expected a type", so the length becomes the range `0..n`, a second
  spelling of the same fact. Naming `n` separately costs a line for a value
  used once. The dream's `Mod<1e9+7>` alias `Z` is also inlined here to keep
  the port inside the dream-token ratchet, so `HashMap<Int, Mod<1e9 + 7>>` is
  the only place the modulus is written.
- **Goal it hurts:** express (one spelling per idea).
- **Ideal code:** `let a: [read(1..=2e5)]1..=1e9 = read()`.
- **General fix (core lane):** accept an `Int`-valued expression as an array
  length in a type, meaning `0..len`, everywhere a `[D]T` type is accepted,
  as `read<[n]T>()` already does.
- **Dream:** `dream/cf2066c.cp` line 4.
- **Severity:** low.
- **Area:** core
