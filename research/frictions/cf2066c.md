# cf2066c — Bitwise Slides

The editorial's DP: after each step two of `P, Q, R` are equal (to some `x`)
and the third is the prefix xor, and of `ways[x]` only the entry for the
previous prefix changes, so the whole DP is one hash-map update per element.

## A map read with a default needs `.get(k) ?? 0` at every use
- **Where:** `cf2066c.cp`, line 12:
  ```cp
  ways[pre] = 3 * (ways.get(pre) ?? 0) + 2 * (ways.get(pre ^ x) ?? 0)
  ```
- **What felt wrong:** The DP is sparse over xor values, so `ways` is a map
  whose absent keys mean zero. `ways[k]` traps when absent, so every read
  spells the default again; the default is a fact about the map, repeated at
  each read, and the formula no longer reads like the recurrence
  `ways[pre] = 3 * ways[pre] + 2 * ways[pre ^ x]`. Turning a `[D]Z` DP into a
  map DP (the common revision when values are large) rewrites every read.
- **Goal it hurts:** express and revise (one fact in one place; array to map
  is supposed to be a local edit).
- **Ideal code:**
  ```cp
  var ways: HashMap<Int, Z> = [0: 1] default 0
  for x in a:
      ways[pre] = 3 * ways[pre] + 2 * ways[pre ^ x]
      pre ^= x
  print(sum(ways.values))
  ```
- **General fix:** a map declared with a default (`design/spec/26-containers.md`
  sparse maps; `Map.with_default(z)` or a `default` clause) whose reads return
  the default without inserting, so a dense array and a sparse map share the
  same indexing code. The same mechanism covers counters (`default 0`) and
  adjacency maps (`default []`).
- **Dream:** `dream/cf2066c.cp` lines 7 and 10: the default is declared once and every read is `ways[k]`.
- **Severity:** medium.

## Maps have no `.values` / `.keys` views
- **Where:** `cf2066c.cp`, line 14: `print(sum(v for (_, v) in ways))`.
- **What felt wrong:** `sum(ways.values)` is the guess (Python, Rust, C++
  ranges all have it) and fails with `E0203: no member values`; the pair
  destructuring with a discarded key is the only spelling.
- **Goal it hurts:** express (guessable APIs).
- **Ideal code:** `print(sum(ways.values))`.
- **General fix:** `.keys` and `.values` iterators on `Map`, `HashMap` and
  arrays over a domain, as the same `Seq` views `for (k, v) in m` already uses.
- **Dream:** `dream/cf2066c.cp` line 12.
- **Severity:** low.

## The constraint `a_i >= 1` lives only in prose
- **Where:** `cf2066c.cp`, line 5: `let a: [0..n]Int = read()`.
- **What felt wrong:** the original filters zeros and multiplies by `3^zeros`,
  defending against inputs the statement forbids; the port relies on
  `1 <= a_i` silently. Writing `[0..n]1..=1_000_000_000` would validate it, but
  then `pre ^= x` on a ranged value needs the xor result type to be plain
  `Int`, and it is not obvious from the docs whether ranged values xor into
  `Int` or trap; I kept `Int` rather than guess.
- **Goal it hurts:** hard to get wrong (constraints written once as types).
- **Ideal code:** `let a: [0..n]1..=10^9 = read()` with `pre: Int` accepting
  `pre ^ a[i]` as an `Int`.
- **General fix:** document (and test) that bitwise operations on ranged
  integers widen to `Int`, like `+` does, so statement ranges can be copied
  into every input type without second-guessing.
- **Dream:** `dream/cf2066c.cp` lines 4 and 11: the statement range is the input type and `pre ^= x` stays `Int`.
- **Severity:** low.
