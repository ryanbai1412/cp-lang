# cf2183e — LCM is Legendary Counting Master

The editorial idea fits the language well: `1/lcm(x, y) <= 1/x - 1/y`, so a
good sequence starts at 1 and steps `x -> x + d` with `d | x`; count the
completions with a value-indexed DP. The frictions are around the edges: the
input's "0 means free" convention, a range method that silently allocates,
and the rolling-buffer DP.

## `read(none: 0)` cannot read a ranged array of optionals
- **Where:** `cf2183e.cp`, lines 8, 11 and 16–17:
  ```cp
  let a: [0..n]0..=m = read()
  if a[0] in [0, 1]: ways[1] = 1
  ...
      if a[i] != 0:
          for x in 1..=m if x != a[i]: next[x] = 0
  ```
- **What felt wrong:** `a_i = 0` means "not fixed". The cheat sheet says
  `read(none: 0)` reads `?Int` with `0` as none, so the natural declaration is
  `let a: [0..n]?(1..=m) = read(none: 0)`. It fails with `E0302: read() can't
  tell how much a [Int]?Int is`, and the help suggests `let a: [n]Int` — which
  drops both the optional and the range. The port falls back to the sentinel
  `0` and tests `!= 0` and `in [0, 1]` by hand, the exact "absent vs valid"
  confusion the language promises to keep apart. The message also prints the
  array as `[Int]?Int` although its length `n` is right there.
- **Goal it hurts:** hard to get wrong (sentinels), doubt to evidence (error).
- **Ideal code:**
  ```cp
  let a: [0..n]?(1..=m) = read(none: 0)
  if a[0] in [none, 1]: ways[1] = 1
  ...
      if let v = a[i]: next.keep_only(v)
  ```
- **General fix:** make `read(none: s)` compose with every readable element
  type, including arrays of ranged optionals (the length comes from the
  array's domain as for any array read). The error should name the real
  missing piece rather than suggest dropping the type.
- **Dream:** `dream/cf2183e.cp` lines 8, 10 and 14: `[0..n]?(1..=m) = read(none: 0)`, `in [none, 1]`, `if let v = a[i]`.
- **Severity:** medium.

## `(lo..=hi).step(k)` materializes a `List` and costs 6.7x
- **Where:** first draft of `cf2183e.cp` line 15, now:
  ```cp
  for j in 1..m / d: next[(j + 1) * d] += ways[j * d]
  ```
- **What felt wrong:** the obvious loop over multiples of `d` is
  `for x in (d..=m - d).step(d): next[x + d] += ways[x]`. It type-checks and is
  what the spec documents, but the emitted C++ builds a `std::vector<ll>` of
  every step before looping (`steps.push_back(i_2)`), inside the O(m log m)
  inner loop of an O(n m log m) DP. On the max input it ran 283 ms against the
  original's 42 ms; rewriting it as an index multiply brought it to parity.
  Nothing in the source says the range is allocated, so the contestant cannot
  see the cost ("anything that looks O(1) is O(1)").
- **Goal it hurts:** performance, the obvious way is the fast way.
- **Ideal code:**
  ```cp
  for x in (d..=m - d).step(d): next[x + d] += ways[x]
  ```
- **General fix:** lower `range.step(k)` (and every range adaptor used as a
  `for` source: `.rev`, `.step`) to a counted loop, never a list; add a
  lowering test that `for x in r.step(k)` allocates nothing.
- **Dream:** `dream/cf2183e.cp` line 13: `(d..=m - d).step(d)` as a counted loop.
- **Severity:** high.

## A rolling DP layer needs two declarations, a `fill` and a `swap`
- **Where:** `cf2183e.cp`, lines 9–10, 13 and 18:
  ```cp
  var ways: [1..=m]Z = 0
  var next: [1..=m]Z = 0
  ...
      next.fill(0)
      ...
      swap(mut ways, mut next)
  ```
- **What felt wrong:** "the next layer from the previous one" is one idea but
  four lines in three places, and the type `[1..=m]Z` is written twice. The
  shorter `var next: [1..=m]Z = 0 ... ways = next` (my first draft) allocates a
  fresh array every layer and then copies it into `ways`. Changing the value
  range (say to `0..=m`) is a two-place edit. The spec rejects `roll` and keeps
  `fill` + `swap`; that keeps control flow visible but leaves the duplicated
  declaration.
- **Goal it hurts:** express and revise (each fact in one place),
  performance (the short form copies).
- **Ideal code:**
  ```cp
  var ways, next: [1..=m]Z = 0
  ...
      ways = next.take()   // move, leaves `next` refilled with its default
  ```
- **General fix:** allow one declaration for several variables of the same
  type and initializer, and make `x = y` from a dead or `take()`n local a
  move (no copy), so the short form is also the fast one.
- **Dream:** `dream/cf2183e.cp` lines 9 and 15: one declaration for both layers, and `ways = next.take()`.
- **Severity:** low.

## The interpreter is ~1000x slower than the C++ on the max input
- **Where:** the whole program; the gate needs
  `INTERP_TIMEOUT=150 proto/ports/ecnerwala/gate.sh cf2183e 150`.
- **What felt wrong:** the O(n m log m) ≈ 2.5·10^7-step DP runs in 40 ms as
  C++ and takes 19 s in `cpl run` (see measurements), so the
  default 20 s gate times out on the max-size case and every `cpl run` on a
  big test is a coffee break. The debug interpreter is the tool for doubt
  (traces, traps in source terms); when it cannot run the max test, the
  contestant debugs the case that matters only in the C++.
- **Goal it hurts:** doubt to evidence.
- **Ideal code:** the same program.
- **General fix:** a faster interpreter tier (compiled bytecode with unboxed
  `Int`/`Mod` locals and checked array access), or a `cpl run --release`
  that keeps trap reporting in source terms.
- **Dream:** none; the program is unchanged, the fix is in the tool.
- **Severity:** medium.
