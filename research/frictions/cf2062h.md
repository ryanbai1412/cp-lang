# cf2062h — Galaxy Generator

Galaxies keep merging while two bounding boxes share a row or column
projection, so the final value of a star subset is the number of boxes in a
family with pairwise disjoint row and column projections. Sweep row intervals
`lo..hi` from short to long; `ways[hi][lo][cols]` counts subsets of the stars
in those rows whose boxes all lie in the column set `cols`, and
`galaxies[hi][lo][cols]` sums their box counts. A box `rows mid..hi` times a
column band is a single galaxy for `2^stars - ways[hi][mid][band]` of its
subsets (everything that does not already split into smaller boxes), and it
extends every family of `lo..mid` that avoids its columns. $O(2^n n^5)$ with
a small constant.

## The interpreter is too slow to gate the official samples

- **Where:** the whole port. `cpl run` on the official sample file (three
  $n = 11$ tests plus small ones) takes **54.8 s** (peak RSS 46,592 KB); the
  emitted C++ takes **0.16 s** on the same file, about 340x faster. The
  gate's default `INTERP_TIMEOUT` is 20 s, so `gate.sh cf2062h 150` only
  passes as `INTERP_TIMEOUT=300 proto/ports/ecnerwala/gate.sh cf2062h 150`
  (73 s wall). The random cases are capped at $n \le 9$ for the same reason;
  the $n = 14$ max input was compared C++-to-C++ only.
- **What felt wrong:** the interpreter is the fast-feedback tool ("incomplete
  programs still run"), yet on an exponential DP it is unusable at the sizes
  the samples already contain, so the contestant's loop becomes
  build-compile-run. The port also needs a README timeout entry that this
  lane may not write (shared file).
- **Goal it hurts:** doubt to evidence, dependable submission (the two
  engines are only cross-checked on small inputs).
- **Ideal code:** unchanged; the program is already the editorial.
- **General fix:** a faster interpreter tier for tight integer/array loops
  (typed bytecode or a JIT over the same IR the C++ backend uses), or have
  `cpl run` transparently compile-and-run when a run exceeds a budget, still
  reporting interpreter-quality traps. Until then, the gate should read a
  per-port timeout from the port directory rather than a shared README.
- **Severity:** high
- **Dream:** `proto/ports/ecnerwala/dream/cf2062h.cp` (no source change; the
  fix is in the tool).

## `Mod<P>` is stored as 64 bits and tables nest as vectors of vectors

- **Where:**
  ```
  var ways: [0..=n][0..=n][Cols]Z = 0
  ```
  emits `struct Mod_1000000007_2 { ll v = 0; }` and
  `std::vector<std::vector<std::vector<Mod_1000000007_2>>>`, with
  `cpl::at` checks on the two outer levels inside the innermost loop.
- **What felt wrong:** on the $n = 14$ max input the port takes **0.97 s**
  and **63,536 KB** against the original's **0.66 s** and **32,000 KB**
  (1.47x time, 2x memory) for the same algorithm and loop order. A residue
  below $2^{30}$ fits in 32 bits; the declared type says so, and the
  representation ignores it. There is no in-language way to get the
  original's flat `tensor<num, 3>`: a `[A, B, C]T` product index is the
  documented spelling for grids, but not for cuts `0..=n` times a `Subset`.
- **Goal it hurts:** performance and control ("values take the fewest bytes
  their types allow"; the 1.1x target).
- **Ideal code:**
  ```
  var dp: [Row.spans][Bits<Col>]Tally = (ways: 0, boxes: 0)   // one flat block
  ```
- **General fix:** store `Mod<P>` in the narrowest unsigned word that holds
  `P - 1` (32 bits for both common primes), and lay out nested fixed-size
  arrays (`[A][B][C]T` with every extent known at allocation) as one flat
  allocation with a single bounds proof per loop nest; `cpl explain` should
  show the layout.
- **Severity:** high
- **Dream:** `proto/ports/ecnerwala/dream/cf2062h.cp` line 15.

## No elementwise array add, and the natural spelling was a silent bug

- **Where:** the first draft wrote the "last row holds no box" transition as
  a copy,
  ```
  ways[hi][mid] = ways[hi - 1][mid]
  ```
  which compiles, runs and is wrong (it drops what shorter row intervals
  ending at `hi` already contributed; sample 2 printed 3 instead of 4). The
  intended `ways[hi][mid] += ways[hi - 1][mid]` is rejected (`E0309: + can't
  be applied to [Int]Int and [Int]Int`), so the port spells it as a loop:
  ```
  for cols in Cols:
      ways[hi][mid][cols] += ways[hi - 1][mid][cols]
      galaxies[hi][mid][cols] += galaxies[hi - 1][mid][cols]
  ```
- **What felt wrong:** the one-line whole-table form is the editorial's
  sentence, and the only whole-table form that type-checks (`=`) has a
  different meaning; it was the first thing I wrote and cost a debugging
  round. The loop also repeats the fact for each parallel table.
- **Goal it hurts:** express, hard to get wrong.
- **Ideal code:**
  ```
  dp[mid..hi] += dp[mid..hi.prev]
  ```
- **General fix:** elementwise compound assignment between arrays of the
  same index type (`a += b`, `a max= b`), defined as the obvious loop and
  costing exactly that; a lint when a whole sub-array is overwritten right
  after it was accumulated into.
- **Severity:** medium
- **Dream:** `proto/ports/ecnerwala/dream/cf2062h.cp` line 19.

## Two parallel DP tables instead of one table of pairs

- **Where:** `ways` and `galaxies` are declared, initialised and updated in
  lock-step:
  ```
  let (w, g) = (ways[mid][lo][rest], galaxies[mid][lo][rest])
  ways[hi][lo][rest | band] += w * one_box
  galaxies[hi][lo][rest | band] += (w + g) * one_box
  ```
- **What felt wrong:** the pair (number of subsets, total boxes) is one
  value, the standard "count and sum" semiring element. A tuple element type
  would keep it in one table, but tuples do not get `+` or scalar `*`, so
  every update would be spelled field by field anyway.
- **Goal it hurts:** express and revise (adding a third statistic touches
  every line of the update).
- **Ideal code:**
  ```
  type Tally = (ways: Z, boxes: Z)                     // + and * Z are fieldwise
  dp[lo..hi][rest | band.bits] += (ways: w, boxes: w + b) * one
  ```
- **General fix:** derive fieldwise arithmetic for named tuples whose fields
  are all numeric (opt-in, like `Eq`), so "count and sum" tables are one
  declaration.
- **Severity:** medium
- **Dream:** `proto/ports/ecnerwala/dream/cf2062h.cp` lines 13, 24-25.

## Building row masks and column bands by hand

- **Where:**
  ```
  let grid: [Row]Str = read()
  var stars: [Row]Cols = Cols.empty
  for r in Row:
      for c in Col:
          if grid[r][c.to_idx] == '1': stars[r] = stars[r].with(c)
  ...
  var band = Cols.empty
  for y in y_lo..n:
      band = band.with(Col(y))
      let inside = sum((stars[Row(r)] & band).len for r in mid..hi)
  ```
- **What felt wrong:** a `0`/`1` grid cannot be read as `[Row, Col]Bool`
  (`R0001: 10 is not a Bool`), a subset cannot be built from a predicate or
  a list (`Col.mask` does not exist; `[Row] r => ...` with a comprehension
  fails to type), and a contiguous column interval has no subset form, so the
  band is grown one `.with` at a time. Row intervals are raw `Int` cuts with
  `Row(r)` conversions, and the rectangle count is recomputed per row rather
  than read from a 2D prefix sum.
- **Goal it hurts:** express, hard to get wrong (the cut/position mix in
  `mid..hi` is unchecked).
- **Ideal code:**
  ```
  let star: [Row, Col]Bool = read(as: "01")
  let stars = star.rect_counts()
  for band in Col.spans(order: .inner_first):
      let one = Z(2) ** stars[(rows: mid..hi, cols: band)] - ...
  ```
- **General fix:** a character-set read option for `Bool` grids; `D.mask(xs)`
  and `Bits<D>.of(pred)` (both in `design/spec/21-index-spaces.md`);
  `span.bits` for an interval of a domain; `Row.cuts`/`Row.spans` as index
  spaces so row intervals are typed; a 2D `rect_counts` beside the 1D scans.
- **Severity:** medium
- **Dream:** `proto/ports/ecnerwala/dream/cf2062h.cp` lines 11-12, 20-22.

## What worked

- `Subset<Col>` as an index space: `[Cols]Z` tables, `Cols.full - band`,
  `rest | band` and `for rest in s.subsets` emit exactly the original's
  bit loop (`rest = (rest - 1) & t5`).
- `Mod<P>` arithmetic including `Z(2) ** inside` needed no ceremony.
