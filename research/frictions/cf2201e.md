- **Tokens (contestant-written):** 322 (port; down from 490) vs 807 (original `main`), 0.40x (original total with NTT/mod template: 13,699)

## Algorithm summary

Split `t` of length $2m$ into two halves of length $m$. A valid ABBA string of length $2m$ is determined by its minimal period $L \mid m$ (with $f = m / L$): each half must be $L$-periodic, and under some cyclic shift $k \in [0, L)$ of the second half reversed, every pair of fixed characters must agree. By inclusion-exclusion on the repetition count $f$, each divisor $f \mid m$ contributes weight $\prod_{p \mid f} (1 - p)$ times the number of valid cyclic shifts summed over $2^{\text{free positions}}$.

For each divisor $f \mid m$ (via `std.math.divisors` and `std.math.factor`, with labeled `continue 'divisor` on conflict), encode fixed characters as $\pm 1$ (`sign0`, `sign1`) and presence as $1$ (`fix0`, `fix1`), reversing the second half. Two cyclic convolutions of length $L$ give, for every cyclic shift $i$, the signed agreement sum (`diff_conv[i]`) and the count of doubly-fixed positions (`both_conv[i]`). Shift $i$ has zero conflicts iff `diff_conv[i] == both_conv[i]`, leaving `len - tot_fix + both_conv[i]` free `?` positions.

## Frictions

### 1. [Resolved] No exact-integer convolution or cyclic correlation in `std` / `lib.math.poly`

- **Resolution:** `std.ntt.convolve_int(a, b, cyclic: true)` now handles exact integer cyclic convolution directly, removing the `cyclic_convolve` wrapper, `Mod` encoding of $\pm 1$ arrays, and `both_conv[i].v` extraction.

- **Severity:** high
- **Goal it hurts:** express, performance
- **Area:** math

**What happened:**
The problem needs cyclic correlation of two small-integer sequences (entries in $\{-1, 0, 1\}$, results in $[-m, m]$ with $m \le 2 \cdot 10^5$). `lib.math.poly` only exposes linear `convolve(a: List<Z>, b: List<Z>) -> List<Z>` hard-wired to `Z = Mod<998244353>` (plus 3-prime `convolve_mod`), with no cyclic convolution, no correlation, and no exact-integer NTT.

As a result, the port must:
1. Encode integer arrays into `Mod<998244353>` (`sign0`, `sign1`, `fix0`, `fix1`), relying implicitly on $2m < 998244353$.
2. Manually reverse the second half (`s[1][len - 1 - i]`), which is an off-by-one trap.
3. Write a 5-line `cyclic_convolve` wrapper that allocates a length-$2L-1$ linear product and folds `res[i % len] += prod[i]`.
4. Reach into the internal field `both_conv[i].v` to recover an `Int` index for `pow2[...]`.

**Current code:**
```cp
fn cyclic_convolve(a: List<Z>, b: List<Z>, len: Int) -> List<Z>:
    let prod = convolve(a, b)
    var res: [0..len]Z = 0
    for i in 0..prod.len: res[i % len] += prod[i]
    res
...
    let diff_conv = cyclic_convolve(sign0, sign1, len)
    let both_conv = cyclic_convolve(fix0, fix1, len)
    for i in 0..len:
        if diff_conv[i] == both_conv[i]:
            ways += pow2[len - tot_fix + both_conv[i].v]
```

**Ideal code:**
```cp
use std.poly.{convolve}

let diff_conv = convolve(sign0, sign1, cyclic: true)
let both_conv = convolve(fix0, fix1, cyclic: true)
for i in 0..len:
    if diff_conv[i] == both_conv[i]:
        ways += pow2[len - tot_fix + both_conv[i]]
```

**General fix:**
Provide polynomial/NTT convolution in `std.poly` (or promote `lib.math.poly`) with:
- Overloads / generic support for both `Mod<P>` and exact `Int` (using a single NTT prime when the result fits or CRT when needed, with documented range/cost), and
- Named options `cyclic: Bool = false` (or `mod_len: ?Int`) and `correlate` / `.rev` support so cyclic correlation does not require a manual fold wrapper or raw `len - 1 - i` indexing.

### 2. Reaching into `Mod<P>.v` leaks internal representation

- **Severity:** medium
- **Goal it hurts:** coherence, express
- **Area:** math

**What happened:**
`both_conv[i]` has type `Z` (`Mod<998244353>`), and indexing `pow2[len - tot_fix + both_conv[i].v]` requires extracting the underlying `Int`. There is no `Int(z)` conversion or documented `.to_int` method; the contestant must know the internal struct field name `.v` from `stdlib/mod.cp`.

**Current code:**
```cp
ways += pow2[len - tot_fix + both_conv[i].v]
```

**Ideal code:**
With exact `Int` convolution (Friction 1), `both_conv[i]` is already an `Int`. When converting a `Mod<P>` to `Int` is genuinely needed (e.g. hashing or table lookup), it should use the same explicit conversion spelling as other types:
```cp
ways += pow2[len - tot_fix + Int(both_conv[i])]
```

**General fix:**
Support `Int(x)` (or a uniform `to_int` protocol) for `Mod<P>` rather than relying on the unguessable field `.v`.

---

### 3. No `prod(...)` reduction to match `sum(...)`

- **Status:** fixed: `prod(...)` is in the prelude and `cf2201e.cp` line 49 uses `let w = prod(Z(1 - p) for (p, _) in factor(f))`.
- **Severity:** low
- **Goal it hurts:** express
- **Area:** seq

**What happened:**
Computing the inclusion-exclusion weight $\prod_{p \mid f} (1 - p)$ requires a 2-line mutable accumulator loop:
```cp
var w: Z = 1
for (p, _) in factor(f): w *= 1 - p
```
While `sum(...)` works directly over comprehensions (`sum(x for x in xs)`), there is no `prod(...)` counterpart (or general `fold` on generator expressions).

**Ideal code:**
```cp
let w: Z = prod(1 - p for (p, _) in factor(f))
ans += ways * w
```

**General fix:**
Add `prod` alongside `sum` in `std.prelude` (and/or a general monoid/generator `fold`), using the same multiplicative identity (`1` / `T.one`) and type-inference rules as `sum`.

## What worked well

- `std.math.{divisors, factor}` eliminated both the $O(m)$ divisor scan and a hand-written trial-division loop.
- Labeled `'divisor: for f in divisors(m):` with `continue 'divisor` eliminated the `ok` boolean flag and two nested `if not ok: break` guards.
- Ranged arrays `[0..len]Z = 0` coerced cleanly to `List<Z>` for `convolve`, and 2D ranged optionals `var s: [0..2][0..len]?Char = none` kept the folding pass compact and zero-overhead.
- `Mod<P>` mixed arithmetic (`w *= 1 - p`, `sign0[i] = if c == 'a': 1 else: -1`) required zero `Z(...)` wrappers.
- The port is 25–30% faster and uses less memory than ecnerwala's Goldilocks-packed C++ NTT on both max-size benchmarks.

## No cyclic correlation

- **Goal it hurts:** express
- **Severity:** low
- **Area:** stdlib
- **Status:** open
- **Dream:** `proto/ports/ecnerwala/dream/cf2201e.cp:43-44`
  (`correlate(x.map(sign), y.map(sign), cyclic: true)`)
- **Actual:** `proto/ports/ecnerwala/cf2201e.cp:43-44` convolves with
  `y.map(...).reversed()`, so the shift index is reversed too (harmless here:
  every shift is summed).
- **General fix:** `correlate(a, b, cyclic:)` beside `convolve_int` in
  `std.ntt`, the form string-matching-with-wildcards problems want.

## Folds over a list of optionals and over factor pairs

- **Goal it hurts:** express
- **Severity:** low
- **Area:** stdlib
- **Status:** open
- **Dream:** `dream/cf2201e.cp:45` (`x.sum(known)`), `48`
  (`factor(f).product(p => Z(1 - p.prime))`)
- **Actual:** `cf2201e.cp:45` counts with `c is some`; `48` uses the free
  `prod(... for (r, _) in factor(f))`. `List<?Char>.sum(f)` and
  `List<(Int, Int)>.product(f)` are rejected (no method), and `factor`
  returns bare pairs, so a lambda cannot destructure them by name.
- **General fix:** `sum`/`product` with a mapping function on every list
  (§53), and named fields `(prime, exp)` on `factor`'s pairs.
