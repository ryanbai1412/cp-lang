# cf2066e — Tropical Season

- **Source:** Codeforces 2066E (`proto/ports/ecnerwala/cf2066e_orig.cpp`)
- **Port:** `proto/ports/ecnerwala/cf2066e.cp`
- **Status:** Ported (`gate.sh cf2066e 150` passes; max-size `n = q = 200_000` diff agrees byte-for-byte, but CP Lang is 6.11x slower and would TLE the 4s limit)

## Measurements

- **Tokens (contestant-written):** `698` (CP Lang) vs `1067` (C++ `main()`, `1078` total) — **0.65x**
- **Max-input runtime** (`n = 200_000, q = 200_000`, 500 spaced large barrels + 199,500 random barrels, 3-run median): `7994.0 ms` (CP Lang) vs `1307.8 ms` (C++ `g++ -O2 -std=c++20`) — **6.11x** (exceeds both the 1.5x goal and the 4s problem TL!)
- **Peak RSS (max input):** `70252 KB` (CP Lang) vs `22272 KB` (C++) — **3.15x**
- **Emitted C++ size:** `24887 bytes` (limit 65,536 bytes)

## Algorithm

A state is `No` iff there exists `k > 0` such that `sum(barrels < k) < k`, at least two barrels are `>= k`, and every gap between consecutive barrels `>= k` is `>= k`. Split at `RT = 1000 = sqrt(10^6)`:
- Large `k > RT`: walk downwards from the largest barrel in the ordered multiset `cur`, stopping as soon as the minimum gap drops to `<= RT` (at most `RT` steps).
- Small `k <= RT`: maintain `small_gaps[l]` for every adjacent gap `l in 0..=RT` and `cnt_small[v]` for `v in 0..=RT`, then sweep `k = 1..=RT` in `O(RT)`.

## Frictions

### 1. `SortedBag<K>` lacks O(1) ordered iteration/cursors, turning O(q sqrt(M)) into O(q sqrt(M) log n) — 6.11x slower (critical)

`SortedBag<K>` is the only ordered set/multiset in `stdlib`, and it exposes only root-to-leaf queries (`last_lt`, `first_gt`, `count`), with no ordered iterator or reverse walk (`for (v, c) in cur.rev` or cursor `prev`/`next`). This hurts in two places:
- In `has_bad_k()`, walking the top `<= 500` barrels calls both `cur.last_lt(cur_val)` and `cur.count(nv)` on every step — two `O(log n)` treap traversals per element instead of one `O(1)` amortized iterator decrement (`++it` on `std::set::rbegin()`).
- In `insert_barrel`/`remove_barrel`, finding neighbors requires four separate `O(log n)` calls (`count`, `add`/`remove`, `last_lt`, `first_gt`) instead of one `insert`/`find` + `O(1)` `prev(it)`/`next(it)`.

On `n = q = 200_000`, this makes the CP Lang port run in `7994 ms` vs `1308 ms` for C++ (`6.11x`, TLE on a 4s judge limit).

**Ideal code:**
```cp
for (nv, mult) in cur.entries.rev:
    ...
    if cur_gap <= RT or mult >= 2: break
```
**General fix:** Back `Set<T>` / `Counter<T>` (per `design/spec/26-containers.md`) with a balanced tree (or `std::set`/`std::map` in C++ codegen) that supports `O(1)` amortized forward/reverse iteration (`.rev`) and neighbor/cursor queries without re-traversing from the root.

### 2. `SortedBag<K>` leaks removed treap nodes and uses 6 parallel `Int`/`?Int` lists — 3.15x RSS (high)

In `stdlib/bag.cp`, `make_node` always pushes onto 6 parallel `List`s (`key`, `pri`, `cnt`, `sub`, `left`, `right`) and `remove` never recycles freed indices. Under 200,000 insertions and 200,000 removals, all nodes remain allocated (`70252 KB` vs `22272 KB`, `3.15x` RSS), and every `add`/`remove` executes two recursive `split`s and two recursive `merge`s.

**General fix:** Recycle freed indices via a free list (or lower ordered `Set`/`Map`/`Counter` to `std::set`/`std::map` / a B-tree) and narrow child indices from `Int` (`int64_t`) + `std::optional<int64_t>` (16 bytes each!) to `int32_t` with `-1` sentinel (4 bytes each).

### 3. `SortedBag.add()` and `.remove()` return `Bool`, forcing `let _ =` discards everywhere (low)

Every mutation (`cur.add(v)`, `cur.remove(v)`, `small_gaps[d].add(lo)`, `small_gaps[d].remove(lo)`) required `let _ = ...` because `add` always returns `true` and `remove` returns `Bool`, and unused return values are disallowed.

**Ideal code:**
```cp
cur.add(v)
small_gaps[d].remove(lo)
```
**General fix:** Follow `design/spec/26-containers.md` where `Counter.add(k)` returns `Unit`, or allow discarding `Bool` returns from mutating container methods without `let _ =`.
