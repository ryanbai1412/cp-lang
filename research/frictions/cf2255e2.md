# cf2255e2 friction

Every version appends each position's value to that position's history, and the answer
is the best subarray of one position's history. A range tag is therefore a function on
(value, history summary). Negate and clamp-to-zero only look at the sign of the value
and scale with its magnitude, so until an assignment a tag is, for each sign, a new sign
plus the history it records per unit of |value|; after an assignment the value is a
constant and the recorded history is fixed. Tags compose in O(1), so one lazy segment
tree over positions answers everything, with a "record" tag applied to the whole range
after each version. The original does the same with a hand-rolled tree and a 3x3 table.

## The idiomatic program is 4.4x slower than the original and blows the time limit
- **Where:** the whole port. Max input (n = q = 500000): original 0.95 s, port 4.20 s
  (the limit is 3 s). `gprof` of the emitted C++: `then` (tag compose) 35%, `run` 20%,
  `join` 15%, tree internals 13%, `std::function` dispatch 7%; `then` runs 47M times.
- **What felt wrong:** the algorithm and the call counts match the original; the cost is
  representation. Records go into `then`/`run` by value (the signature in the emitted C++
  takes the 3-path tag tuple by value), every `?Seg` is a `std::optional` of a 4-tuple, and
  `Action`'s four closures are called through `std::function`, so nothing inlines. The
  natural first version, a `[-1..=1]Path` array inside the tag, was slower still (6.0 s,
  296 MB): a small fixed-size array lowers to a heap `std::vector` per tag. Spelling the
  three paths as fields bought 25% and the `path(f, s)` selector below.
- **Goal it hurts:** performance (max 1.5x of C++), and "the obvious way is the fast way".
- **Ideal code:** the port as written, at original speed.
- **General fix:** pass records by `const&` when the callee does not move them; lower
  arrays over a constant-size domain to `std::array`; make `Action`/`Monoid` operations
  template parameters (or functors the compiler monomorphises) instead of
  `std::function`; give `?T` of a record a niche or flag layout without `std::optional`'s
  copy cost. Helps every lazy-tree port with a nontrivial tag (all of them).
- **Dream:** `dream/cf2255e2.cp` lines 13-20 (the same tag code; the fix is in the lowering).
- **Severity:** high.

## An enum cannot index an array, so a three-way case is a range type and an if-chain
- **Where:** `type Sign = -1..=1`, `fn sign(v)`, and
  `fn path(f: Tag, s: Sign) -> Path = if s < 0: f.neg elif s == 0: f.zero else: f.pos`.
- **What felt wrong:** the tag is a table indexed by "negative, zero, positive". The
  first spelling, `enum Sign: Neg, Zero, Pos` with `[Sign]Path`, fails:
  `error[E0302]: Sign is a type, and a value is needed here`. A range domain works but
  then the table must be fields (for speed, above) plus a hand-written selector, so each
  table entry is named three times (field, constructor, selector).
- **Goal it hurts:** express, coherence (enums are the natural index space for a case
  split; domains are already index spaces).
- **Ideal code:**
  ```cp
  enum Sign: Neg, Zero, Pos
  type Tag = (path: [Sign]Path, set: ?Cell)
  fn run(f: Tag, c: Cell) -> Cell:
      let p = f.path[sign(c.val)]
  ```
- **General fix:** a payload-free enum is a domain (`[E]T`, `for e in E`, `E.len`),
  stored as a fixed array. Helps every "per state" table (DP over a small automaton,
  direction tables).
- **Dream:** `dream/cf2255e2.cp` lines 8, 11, 14 and 20.
- **Severity:** medium.

## A dual segment tree needs a fake monoid
- **Where:** `over: Monoid(id: blank, op: (c, d) => c)`; the program only ever calls
  `st.apply(range, f)` and `st.get(p)`.
- **What felt wrong:** "range-apply, point-get" needs no fold at all, but `LazySegTree`
  demands an `over` monoid and pulls it on every update. The `op` written here is not
  even associative-meaningful; it exists to satisfy the signature, and the tree still
  pays for `2 log n` pulls per update.
- **Goal it hurts:** express (a fact the program does not have), performance.
- **Ideal code:** `var st = DualSegTree<I, Cell>(tags, [I] i => (a[i], one(a[i])))`
  with `Action(id:, compose:, apply:)` and no `over`.
- **General fix:** a stdlib range-update point-query tree whose `Action` has no fold
  (or `LazySegTree` accepting a missing `over` and dropping pulls), documented O(log n)
  per call.
- **Dream:** `dream/cf2255e2.cp` line 35.
- **Severity:** medium.

## An optional tuple literal cannot be the identity without a named, annotated binding
- **Where:** `let blank: Cell = (0, none)` used once, as `Monoid(id: blank, ...)`.
- **What felt wrong:** `Monoid(id: (0, none), ...)` does not infer `?Seg` for the `none`
  from the action's other closures, and lambda parameters cannot be annotated to help
  (`(c: Cell, d: Cell) => c` is `error[E0103]: expected , or ) in the lambda's
  parameters, found :`). A single-use binding exists only to carry a type.
- **Goal it hurts:** express, revisable (unguessable where the annotation must go).
- **Ideal code:** `over: Monoid(id: (0, none), op: (c, d) => c)` or `(0, none): Cell`.
- **General fix:** infer constructor-argument types from the generic's other arguments
  (bidirectional inference through `Action`), plus annotated lambda parameters and an
  ascription expression `e: T`.
- **Dream:** `dream/cf2255e2.cp` lines 29 and 35 (`Seg.empty`; no identity cell is needed).
- **Severity:** low.

## The max-subarray monoid is written again
- **Where:** `type Seg = (best, total, pre, suf)`, `join`, `scaled`, `one`.
- **What felt wrong:** this four-field summary is the most common segment-tree monoid in
  contest code and every port writes the same `join`, with `?Seg` for the empty segment
  and two `?? return` lines because the identity has no finite value.
- **Goal it hurts:** express, hard-to-get-wrong (`max(x.pre, x.total + y.pre)` typos).
- **Ideal code:** `type Seg = MaxSub<Int>`; `Seg.one(v)`, `a + b`, `a * k`.
- **General fix:** a stdlib `MaxSub` monoid next to `Sum`/`Min`, with `none` as its
  identity and scaling by a non-negative constant.
- **Dream:** `dream/cf2255e2.cp` lines 1, 7 and 15.
- **Severity:** low.

## The interpreter cannot run the max input
- **Where:** `cpl run cf2255e2.cp < max.in` did not finish in 300 s.
- **What felt wrong:** the gate's random cases are small, so this does not block the port,
  but "is my program right on the big case?" needs the compiled path.
- **Goal it hurts:** evidence.
- **General fix:** interpreter speed on closure-heavy `Action`s, or `cpl run --native`.
- **Dream:** `dream/cf2255e2.cp` the whole program, unchanged, under `cpl run`.
- **Severity:** low.
