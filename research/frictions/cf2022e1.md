# cf2022e1 — Billetes MX (Easy Version)

The editorial: a grid is beautiful iff every cell is `row[r] xor col[c]`
for some row and column labels. A fixed cell is the constraint
`row[r] xor col[c] = v`, so rows and columns are vertices of one graph
and each component has a single free 30-bit label, less one for the global
xor shift that changes no cell. A contradictory cycle gives 0; otherwise
the count is `2^(30·(components − 1))`. One union-find with xor potentials.

## No xor-potential union-find, so the port writes one
- **Where:** `cf2022e1.cp`, lines 7–25: `up`, `size`, `gap`, `find` and
  `unite`, a hand-written union-find with xor labels.
- **What felt wrong:** the stdlib has `ParityDsu` (potentials in `Bool`)
  and `PotentialDsu` (potentials in `Int` under `+`), but this problem
  needs potentials in `0..2^30` under `xor`. `ParityDsu`'s doc says it is
  for `x[a] xor x[b] == d`, which holds only for one bit. My first port used
  one `ParityDsu` per bit (30 of them, leaning on the bits being
  independent): on the max input that took 0.29–0.36 s and 72 MB against
  the original's 0.01 s and 4 MB. The hand-written structure is 0.01 s and
  8 MB, but it is a stdlib algorithm rewritten in the port, with its own
  union by size and its own label convention.
- **Goal it hurts:** express; performance (the obvious stdlib path was
  30x slower); coherence (two structures that are one structure over
  different groups).
- **Ideal code:** `var labels = PotentialDsu<Line>(xor)` and
  `labels.unite(Row(r), Col(c), v)`.
- **General fix (dsu):** make `PotentialDsu` generic over an abelian group
  (`+` on `Int`, `xor` on bit ranges, `+` on `Mod`); `ParityDsu` becomes
  the `xor` instance over `Bool`.
- **Dream:** `dream/cf2022e1.cp` lines 9, 11.
- **Severity:** high.
- **Area:** dsu

## Rows and columns share an index space by offsetting
- **Where:** `cf2022e1.cp`, lines 4, 27: `domain Line = 1..=n + m` and
  `Line(cell.r), Line(n + cell.c)`.
- **What felt wrong:** rows and columns are two different things the
  contestant knows apart, which is exactly what domains exist for, but a
  union-find needs one index type, and the only way to make one is to
  offset columns by `n` by hand. Nothing stops `Line(c)` for a column.
- **Goal it hurts:** hard to get wrong (wrong index space).
- **Ideal code:** `domain Line = Row(1..=n) | Col(1..=m)` with
  `Row(r)`, `Col(c)`.
- **General fix (core):** sum domains: a disjoint union of domains with
  tagged constructors, stored as one dense range (`to_idx` of `Col(c)` is
  `n + c`), usable as `[Line]T` and `Dsu<Line>`.
- **Dream:** `dream/cf2022e1.cp` lines 8, 11.
- **Severity:** high.
- **Area:** core

## No component count on union-find
- **Where:** `cf2022e1.cp`, line 28:
  `let parts = sum(Int(up[x] == x) for x in Line)`
- **What felt wrong:** the answer is a function of the number of
  components, which every union-find knows in O(1) (n minus successful
  merges), yet it must be recounted by scanning for roots. `Line.count(p)`
  also doesn't exist: on a domain `.count` is the size, so the predicate
  form is a type error (`expected Str, found domain`), and the count is a
  `sum` of `Int(...)`.
- **Goal it hurts:** express; guessable APIs.
- **Ideal code:** `labels.components`.
- **General fix (dsu, seq):** a `components` getter on every DSU;
  `count(p)` on domains named so it doesn't collide with the size.
- **Dream:** `dream/cf2022e1.cp` line 12.
- **Severity:** medium.
- **Area:** dsu

## `Mod` power is `**` and the literal zero needs a type
- **Where:** `cf2022e1.cp`, line 29: `Z(2) ** (30 * (parts - 1)) else: Z(0)`.
- **What felt wrong:** the error for `.pow` is clear (`power uses **`),
  but the `else` branch has to say `Z(0)`; a bare `0` doesn't take the
  type of the other branch.
- **Goal it hurts:** express.
- **Ideal code:** `if consistent: Z(2) ** (...) else: 0`.
- **General fix (core):** type `if`/`else` branches against each other
  before defaulting an integer literal.
- **Dream:** `dream/cf2022e1.cp` line 12.
- **Severity:** low.
- **Area:** core
