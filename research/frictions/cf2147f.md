# cf2147f — Exchange Queries

## `Action` and `Monoid` lower to `std::function` closures, causing 2.97x slowdown in `LazySegTree`
- **Where:** `cf2147f.cp`, lines 19–25:
  ```cp
  let act = Action<?Node, Int>(
      id: 0,
      compose: (f, g) => f + g,
      apply: (f, x, _) => if let v = x: Node(v.mn + f, v.first, v.last, v.pairs) else: none,
      over: Monoid(id: none, op: merge),
  )
  var seg = LazySegTree<Cut, ?Node>(act, [Cut] c => Node(0, c.to_idx, c.to_idx, 0))
  ```
- **What felt wrong:** Every `pull`, `put`, and `push` in `LazySegTree` calls `act.over.op`, `act.apply`, and `act.compose` through `std::function` fields in the emitted C++, blocking GCC from inlining them in the O(q log n) hot loop. On `n = 100_000, q = 100_000`, the `?Node` port takes 416.9 ms vs 140.3 ms for the original C++ (2.97x; even with a non-optional `INF`-sentinel `Node`, it still takes 232.6 ms, 1.67x). Additionally, `LazySegTree` allocates a `span` array even though `apply` ignores `_span`, and uses `2 * bit_ceil(n + 1)` leaves with full top-down `push`, whereas a non-negative-lazy tree only needs upward pulls.
- **Goal it hurts:** performance.
- **Ideal code:**
  ```cp
  impl Monoid for ?Node:
      id = none
      fn op(l, r) = merge(l, r)
  impl Action<?Node> for Add:
      id = Add(0)
      fn then(a, b) = Add(a.0 + b.0)
      fn apply(a, x) = x.map(v => Node(v.mn + a.0, v.first, v.last, v.pairs))
  var seg = SegTree<Val.Cut, ?Node, Add>(init: [Val.Cut] c => Node(0, c.to_idx, c.to_idx, 0))
  ```
- **General fix:** Make `Monoid` and `Action` traits statically monomorphized in `SegTree<D, M, A>` (as in spec 27.2), so `op`/`apply`/`then` inline directly with zero `std::function` indirection; omit the `span` array when `apply` does not request it. Helps every custom `SegTree` and `LazySegTree` port.
- **Severity:** high.

## `?Node` is not niche-packed inside `LazySegTree`, nearly doubling runtime (232.6 ms -> 416.9 ms)
- **Where:** `cf2147f.cp`, lines 2–10 and 25:
  ```cp
  struct Node(mn: Int, first: Int, last: Int, pairs: Int)
  ...
  var seg = LazySegTree<Cut, ?Node>(act, [Cut] c => Node(0, c.to_idx, c.to_idx, 0))
  ```
- **What felt wrong:** Using idiomatic `?Node` instead of a magic `const INF = 1 << 60` sentinel makes the code cleaner and removes a sentinel bug class, but `?Node` lowers to `std::optional<Node>` (adding an 8-byte alignment-padded tag to every node and extra branches) rather than exploiting the `INT64_MIN` niche already present in `Node.mn: Int`. Switching from `INF`-sentinel `Node` to `?Node` increased max-input runtime from 232.6 ms (33.3 MB RSS) to 416.9 ms (39.0 MB RSS).
- **Goal it hurts:** performance, hard-to-get-wrong.
- **Ideal code:**
  ```cp
  // Same `?Node` source, lowered with niche packing on `mn: Int` (32 bytes, same size as `Node`).
  ```
- **General fix:** Propagate niche values from `Int` (and domain/range) fields up to enclosing structs so `?Struct` uses an existing field's niche with zero size overhead, matching Rust's niche optimization and spec 11/18. Helps every custom monoid or DP state that uses `?Struct` as its identity/absent value.
- **Severity:** high.

## `LazySegTree<Bounds<Val>, ...>` fails to typecheck, forcing a separate `Cut = 0..=n` domain
- **Where:** `cf2147f.cp`, lines 14–17 and 28–30:
  ```cp
  domain Item = 1..=n
  domain Cut = 0..=n
  var p: [Item]1..=n = read()
  var s: [Item]1..=n = read()
  ...
  if lo < hi: seg.apply(Cut(lo)..Cut(hi), delta)
  ```
- **What felt wrong:** The permutation values belong to `domain Val = 1..=n`, and the segment tree naturally lives on the `n + 1` cuts `Val.bounds` (`Bounds<Val>`). Passing `Bounds<Val>` as the index domain of `LazySegTree` fails with `E0302: expected ?[Int]Int, found [Val.bounds]Int`, forcing a raw `1..=n` value type plus an unrelated `domain Cut = 0..=n` and manual `Cut(lo)..Cut(hi)` casts.
- **Goal it hurts:** hard-to-get-wrong, express, coherence.
- **Ideal code:**
  ```cp
  domain Val = 1..=n
  var p: [Item]Val = read()
  var s: [Item]Val = read()
  var seg = SegTree<Val.Cut, ?Node, Add>(init: [Val.Cut] c => Node(0, c.to_idx, c.to_idx, 0))
  ...
  if lo < hi: seg.apply(lo.after..hi.after, Add(delta))
  ```
- **General fix:** Make `D.Cut` / `Bounds<D>` a first-class `Index` domain accepted by generic containers (`SegTree`, `LazySegTree`, `Fenwick`) and cut-bounded ranges. Helps every problem indexing cuts alongside elements.
- **Severity:** medium.

## `swap(mut p[i], mut p[j])` is rejected even when `i != j`
- **Where:** `cf2147f.cp`, lines 39–40:
  ```cp
  if tp == 1: (p[i], p[j]) = (p[j], p[i])
  else: (s[i], s[j]) = (s[j], s[i])
  ```
- **What felt wrong:** The natural way to swap two elements of an array is `swap(mut p[i], mut p[j])`, but the borrow checker rejects it with `E0601: p[i] and p[j] may be the same storage`. Parallel tuple assignment `(p[i], p[j]) = (p[j], p[i])` works for `Int`, but for non-copy element types (like `List` or structs) or when teaching one swap idiom, `p.swap(i, j)` exists on `List` yet not uniformly on `[D]T` arrays.
- **Goal it hurts:** express, coherence.
- **Ideal code:**
  ```cp
  if tp == 1: p.swap(i, j)
  else: s.swap(i, j)
  ```
- **General fix:** Provide `.swap(i, j)` on `[D]T` arrays (matching `List.swap`, O(1) even for non-copy elements and safe when `i == j`). Helps every permutation/array swap problem.
- **Severity:** low.
