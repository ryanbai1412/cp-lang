# cf2135f friction

Sort the nodes of a full binary tree by the growth of `f_u`, where a leaf is `x` and an
inner node is `f_l ^ f_r`. Unrolling the left spine, `f_u = x ^ (product of f over the
right children on u's left spine)`, so a node is the multiset of those right children,
compared largest first. A node only contains values of lower generation
(`gen = max(gen l, gen r + 1)`) and beats every value of a lower generation, so ranking
generation by generation gives each distinct value an increasing key. Each multiset is a
persistent segment tree over keys with random-weighted hashes: equal hashes mean equal
sets, and two sets differ first at the largest key whose subtree hashes differ. The
original does the same with three-level layouts and a pair-of-moduli hash; the port uses
one tree over all keys and a `U64` wrapping hash.

## `sorted` ignores a user `impl Ord` in the interpreter
- **Status:** fixed: `Builtin::Sorted`, `Builtin::Min`, and `Builtin::Max` in `cpl-interp` now dispatch through `merge_sort_ty`/`cmp_ty_val` (matching `ExprKind::Sort` and C++17). `cf2135f.cp` now writes `let ranked = [Ranked(set[v], v) for v in by_gen[g]].sorted()`, with parity test `crates/cpl-cli/tests/parity/sorted_ord.cp`.
- **Where:** `var ranked = [...]; sort(mut ranked)` instead of
  `for x in sorted([...])`.
- **What felt wrong:** with `struct R(a, b)` and `impl Ord for R: fn lt(x, y) = x.b > y.b`,
  `sorted(xs)` in `cpl run` orders by the fields (`1 2 3`) while the C++ build honours
  `lt` (`2 3 1`); `sort(mut xs)` honours it in both. The first version of the port used
  `sorted` and failed most random cases in the interpreter only. A program whose engines
  disagree on valid input is the worst kind of surprise: the local run is wrong, the
  submission is right, and nothing warns.
- **Goal it hurts:** dependable submission (interpreter and C++ agree), hard to get wrong.
- **Ideal code:** `for x in sorted(ranked)` (or a comparator, below).
- **General fix:** one sort implementation for `sort` and `sorted` in the interpreter that
  dispatches through `Ord`; a parity test over user `Ord` types.
- **Dream:** `dream/cf2135f.cp` line 30.
- **Severity:** high.

## A persistent hashed multiset is 30 lines of arena code over `Int` handles
- **Where:** `struct Node(l, r, cnt, h)`, `var pool = [Node(0, 0, 0, U64(0))]`,
  `fn insert`, `fn less`, the `Rng` weights, and `set: [V]Ix` holding pool indices.
- **What felt wrong:** "the multiset of right-spine children, compared from the top" is
  one idea, but there is no persistent tree in the stdlib, so the port writes an arena:
  index `0` is a sentinel empty node, handles are bare integers that any `Int` can
  forge, the split point `mid` is recomputed in two functions that must agree, and
  `insert` returns `pool.len - 1` by convention. Any revision (multiplicities, a second
  hash) touches all of it.
- **Goal it hurts:** express, hard to get wrong (an unrelated `Int` indexes the pool).
- **Ideal code:** `set[v] = set[l].with(key[r])`, `set[u].cmp(set[v], desc: true)`.
- **General fix:** `PMultiset<K>` (persistent, hashed segment tree over a key domain) in
  the stdlib with `with`, `==` in O(1) and `cmp` from either end in O(log n); and a typed
  arena (`Arena<T>` with its own handle domain) for the trees it does not cover.
- **Dream:** `dream/cf2135f.cp` lines 21-23 and 29.
- **Severity:** high.

## A custom order needs a wrapper struct and an `impl Ord` over global state
- **Status:** fixed: added `sort(cmp: (a, b) => Bool)` / `sorted(cmp:)` (mutually exclusive with `by:`, composing with `desc: true`), trapping on strict-weak-order violations in `cpl run` and `cpl build --checked` (`cpl::sort_cmp`), with parity test `sort_cmp.cp` and runtime-error test `sort_cmp_strict_weak_order_traps_in_interp_and_checked_cpp`. `cf2135f.cp` now drops `struct Ranked` and `impl Ord for Ranked` and writes `by_gen[g].sorted(cmp: ...)`.
- **Where:** `struct Ranked(t: Ix, v: V)` and `impl Ord for Ranked: fn lt(a, b) = ...`,
  which reads the global `pool`.
- **What felt wrong:** sorting the vertices of one generation by "set, then index" needs a
  new type pairing the handle with the vertex, an `impl` far from the sort, and a
  comparator that reaches into a global. `sorted(xs, by: key)` needs a key that is
  already `Ord`; there is no comparator option.
- **Goal it hurts:** express, revise (the order is defined away from where it is used).
- **Ideal code:** `sorted(by_gen[g], cmp: (u, v) => set[u].cmp(set[v], desc: true) then u <=> v)`.
- **General fix:** a `cmp:` option on `sort`/`sorted`/`min`/`max` taking a three-way
  comparison, and `then` to chain orderings.
- **Dream:** `dream/cf2135f.cp` line 30.
- **Severity:** medium.

## `runs_by` makes the program 50x slower, so runs are found by hand
- **Status:** fixed: `ranked.run_ranges_by(by: x => pool[x.t].h)` in `std.seq` (`2ed3cd3d`) yields `Range<Int>` with zero per-run allocation. The port now uses it (`gate.sh cf2135f 50` passes; max-input `n = 399_999` seed 1 runs in 360.0 ms vs 350 ms manual loop and 18,600 ms old `runs_by` — 51x faster).
- **Where:**
  ```cp
  var last: ?U64 = none
  for x in ranked:
      if last != some(pool[x.t].h):
          keys += 1
          last = some(pool[x.t].h)
  ```
- **What felt wrong:** "one key per run of equal sets" is `runs_by(ranked, x =>
  pool[x.t].h)`, and it gives the right answer, but the max input takes 18.6 s against
  0.35 s for the manual loop (same program otherwise). The emitted helper builds a
  `std::vector` of `(key, std::vector<Ranked>)` per call through a `std::function` and
  copies each run again in the loop. The natural code is a time-limit failure with no
  warning.
- **Goal it hurts:** performance ("the obvious way is the correct and fast way"),
  costs are visible.
- **Ideal code:** `for (_, run) in runs_by(ranked, x => pool[x.t].h): ...`.
- **General fix:** `runs_by` as a lazy generator yielding slices of the input (no copies,
  no `std::function`), with the cost in its doc.
- **Dream:** `dream/cf2135f.cp` lines 31-34.
- **Severity:** high.

## Range-typed fields do not narrow a struct
- **Where:** `type Ix = 0..=10_000_000` and `struct Node(l: Ix, r: Ix, cnt: 0..=400_000,
  h: U64)`.
- **What felt wrong:** the bounds fit in 4 bytes each, but the emitted `Node` is four
  64-bit fields (32 bytes). The pool holds about 7 million nodes; the port peaks at
  224 MB against 56-101 MB for the original's `int` children. Narrowing the fields
  changed nothing (224 MB with `Int` fields too); "arrays pack bounded values tightly"
  does not extend to structs inside a `List`.
- **Goal it hurts:** performance and control (values take the fewest bytes their types
  allow).
- **Ideal code:** the struct as written, 20 bytes.
- **General fix:** store range-typed struct fields at their minimal width, as arrays do.
- **Dream:** `dream/cf2135f.cp` line 24 (keys as `0..n`); the multiset hides the nodes.
- **Severity:** medium.

## Absent children arrive as `0 0` and are decoded at every use
- **Where:** `let kids: [V](Int, Int) = read()` and
  `fn split(v: V) -> ?(l: V, r: V)` that turns `(0, 0)` into `none` and the rest into
  `V(l)`; the `Rooted` adjacency closure also spells `List<V>()` for a leaf.
- **What felt wrong:** the statement's format (0 means no child) is decoded by a helper
  called four times instead of once at the read.
- **Goal it hurts:** express (formats written once, as types).
- **Ideal code:** `let kids: [V]?(l: V, r: V) = read(absent: (0, 0))`.
- **General fix:** a sentinel option on `read` for optional values; `?T.list` for the
  zero-or-one list.
- **Dream:** `dream/cf2135f.cp` lines 12 and 14.
- **Severity:** low.
