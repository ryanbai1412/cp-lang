# cf2062e2 — E2. The Game (Hard Version)

The editorial idea: root the tree at `1` and flatten it by preorder so each subtree is a contiguous range `t.sub(v)`. A node `v` is a winning first move iff the maximum weight `mx` outside `t.sub(v)` strictly exceeds `w[v]`, and every node `u` with `w[u] > w[v]` is covered by one of three disjoint sets: (1) inside `t.sub(v)` (counted by `sub_bit.sum(r)`), (2) attaining `mx` outside `t.sub(v)` (`mx.cnt`), or (3) a root-to-leaf path-prefix-max ancestor whose subtree contains every `mx`-node outside `t.sub(v)` (counted by a difference Fenwick `anc_bit` at `prev_max[mx.lo]`).

## No `Rooted.top_down` fold or `prefix_fold`/`suffix_fold` for monoid prefix/suffix tables
- **Where:** `proto/ports/ecnerwala/cf2062e2.cp` lines 25-52:
  ```cp
  var best_w: [V]Int = 0
  var best_v: [V]?V = none
  var is_path_max: [V]Bool = false
  var prev_max: [V]?V = none
  for p in t.Pre:
      ...
  var pref: [0..=n]MaxInfo<t.Pre> = empty_max
  for p in t.Pre:
      pref[p.ord + 1] = combine(pref[p.ord], cur)
  var suff: [0..=n]MaxInfo<t.Pre> = empty_max
  for p in t.Pre.rev:
      suff[p.ord] = combine(cur, suff[p.ord + 1])
  ```
- **What felt wrong:** Computing path-prefix-max ancestors requires 4 parallel `[V]` arrays and an explicit preorder loop, and computing prefix/suffix monoid folds over `t.Pre` requires two `[0..=n]` arrays indexed by `.ord` and `.ord + 1` instead of `[Bounds<t.Pre>]MaxInfo` via `prefix_fold`/`suffix_fold`.
- **Goal it hurts:** express
- **Ideal code:**
  ```cp
  let (is_path_max, prev_max) = t.top_down((best_w: 0, best_v: none), (st, v) =>
      if w[v] >= st.best_w: ((true, st.best_v), (w[v], some(v)))
      else: ((false, none), st)
  )
  let pref = prefix_fold(wp, MaxInfo.empty, MaxInfo.add)
  let suff = suffix_fold(wp, MaxInfo.empty, MaxInfo.add)
  ```
- **General fix:** Add `prefix_fold` / `suffix_fold` returning `[Bounds<D>]T` (so `pref[r.lo]` and `suff[r.hi]` index directly by `Bounds<Pre>` without `.ord`), and consider a `top_down` pass on `Rooted`.
- **Dream:** `dream/cf2062e2.cp` lines 19-26, 35.
- **Severity:** medium

## No `Fenwick.range_add(Range<D>, T)` helper for difference-array Fenwicks
- **Where:** `proto/ports/ecnerwala/cf2062e2.cp` lines 77-79:
  ```cp
  anc_bit.add(t.pos(v), 1)
  if let after = t.pos(v) + t.size(v):
      anc_bit.add(after, -1)
  ```
- **What felt wrong:** Range-add / point-query on a subtree range `t.sub(v)` requires manually splitting into two `.add` calls and checking `if let after = t.pos(v) + t.size(v)` for the right endpoint.
- **Goal it hurts:** express, hard-to-get-wrong
- **Ideal code:**
  ```cp
  anc_bit.range_add(t.sub(v), 1)
  ```
- **General fix:** Add `Fenwick.range_add(r: Range<D>, x: T)` (or a `RangeAddFenwick<D, T>` wrapper) in `stdlib/fenwick.cp` that handles the right-boundary check internally.
- **Dream:** `dream/cf2062e2.cp` line 44.
- **Severity:** medium

## `W` domain values cannot be compared to `Int` `0` without `.ord + 1`
- **Where:** `proto/ports/ecnerwala/cf2062e2.cp` lines 34, 46, 51, 63:
  ```cp
  if w[v].ord + 1 >= pw:
  ...
  let w_val = weight.ord + 1
  ```
- **What felt wrong:** Storing `w: [V]W` (where `domain W = 1..=n`) lets us bucket by `W` directly, but comparing weights against an `Int` sentinel `0` in `MaxInfo` forces `.ord + 1` in four places instead of storing `?W` or reading `w` as `1..=n` with `group(by:)`.
- **Goal it hurts:** express
- **Ideal code:**
  ```cp
  for bucket in V.group(by: v => w[v]).rev:
  ```
- **General fix:** Provide `V.group(by: v => w[v])` in `stdlib/seq.cp` so `w` can stay `1..=n` (`Int`) without needing a separate `domain W` solely for bucketing.
- **Dream:** `dream/cf2062e2.cp` line 32.
- **Severity:** low
