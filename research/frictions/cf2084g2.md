# cf2084g2 — Wish Upon a Satellite (Hard Version)

Dream program: `proto/ports/ecnerwala/dream/cf2084g2.cp`.

## No stdlib lazy/implicit treap (`LazyTreap` / balanced BST with lazy tags)
- **Where:** `proto/ports/ecnerwala/cf2084g2.cp` lines 4, 16-70, 88-100 vs `dream/cf2084g2.cp` lines 12-23, 35:
  ```cp
  struct SlopeNode(l: ?Int, r: ?Int, pri: U64, sz: Int, slope: Int, add: Int, step: Int)
  ...
  fn split_desc(u: ?Int, val: Int) -> (?Int, ?Int): ...
  fn insert_node(u: ?Int, idx: Int, val: Int, pri: U64) -> Int: ...
  fn collect(u: ?Int): ...
  ```
- **What felt wrong:** Over 65% of the port (~550 of 895 tokens) is hand-rolled arena treap plumbing (`size_of`, `apply_node`, `push`, `pull`, `split_desc`, `insert_node`, `collect`) because `std.bag.SortedBag` has no lazy tag propagation, no position-dependent affine action, and no in-order prefix take. The actual slope-trick algorithm is 12 lines (`cf2084g2.cp` lines 72-86).
- **Goal it hurts:** express, accumulate, hard-to-get-wrong.
- **Ideal code (`dream/cf2084g2.cp:16-23,35`):**
  ```cp
  var slopes = LazyTreap<Int, Affine>(
      order: desc,
      apply: (v, left_sz, f) => v + f.base + left_sz * f.step,
      split: (f, left_sz) => (f, Affine(f.base + (left_sz + 1) * f.step, f.step)),
      compose: (f, g) => Affine(f.base + g.base, f.step + g.step),
  )
  ...
  let best = v0 + slopes.take(half - c0).sum()
  ```
- **General fix:** Add a generic `LazyTreap` / `SeqTree` in `stdlib` supporting custom key order or implicit indexing, subtree-size-aware lazy tag pushdown, split/merge, insert, and lazy in-order views (`take(k)`). Helps every slope-trick, rope, and sequence-reversal/shift problem.
- **Severity:** high.
- **Status:** fixed: `std.lazy.LazyTreap<T, F>` provides an arena-backed randomized treap with subtree-size-aware lazy tag propagation (`apply`, `compose`, `split`, `before`), `insert`, `apply_all`, `apply_range`, `insert_at`, `get`, `take`, and `to_list` with zero `std::function` overhead; `proto/ports/ecnerwala/cf2084g2.cp` now uses it (895 -> 359 tokens, 1.05x of dream).

## `?Int` node indices and `Int` subtree sizes double node memory (2.03x RSS)
- **Where:** `proto/ports/ecnerwala/cf2084g2.cp` line 4:
  ```cp
  struct SlopeNode(l: ?Int, r: ?Int, pri: U64, sz: Int, slope: Int, add: Int, step: Int)
  ```
- **What felt wrong:** Using `?Int` for child indices instead of `-1` sentinels is clean and bug-free, and `sz: Int` is the default integer type, but each `?Int` lowers to 16-byte `std::optional<int64_t>` instead of niche-packing into 8 bytes (or 4 bytes with `0..500_000`). On `n = 500_000`, `nodes` uses `50.7 MB` RSS vs `25.0 MB` for C++ (`2.03x`).
- **Goal it hurts:** performance.
- **Ideal code:** Same `?Int` (or `?(0..500_000)` / `?NodeId`) lowered via niche packing to 4-8 bytes with zero sentinel boilerplate.
- **General fix:** Niche-pack `?Int` (and `?Range`) in codegen, and narrow range-typed struct fields to `int32_t` where static bounds allow. Also helps `cf2066f`, `cf2147f`, and all arena-based data structures.
- **Severity:** medium.

## Concave functions as sorted slopes (slope trick)
- **Goal it hurts:** express-and-revise.
- **Ideal code:** `var best = Concave.point(0)`, then per step
  `best.add_quadratic(c => gain(k, c))` and
  `best.max_convolve(Concave.flat(0..=1))` (dream lines 30-36).
- **Today:** the port hand-builds the slope multiset as a `LazyTreap` with
  three lambdas (`apply`, `compose`, `split` on `left_sz`), tracks the
  domain start `c0` and the value `v0` beside it, and sums
  `slopes.take(half - c0)` at the end.
- **General fix:** `std.slope.Concave`: an integer-indexed concave function
  stored as start, value at start and a sorted slope multiset. Laws:
  max-plus convolution of concave functions merges slope lists
  (`point(d)` shifts, `flat(lo..=hi)` adds zero slopes); adding a quadratic
  adds an arithmetic progression by rank (`add_quadratic` reads its argument
  at three points and debug-checks a fourth); `at(c)` and `max()` read
  the slopes back. The convex twin covers `add_left`/`add_right` slope trick
  (spec/lib/rationale/dp.md). Owner: DP/search lane.
- **Severity:** high (every slope-trick port hand-rolls this).
- **Dream:** `proto/ports/ecnerwala/dream/cf2084g2.cp` lines 17, 30-37
- **Fixed:** `std.slope.{Concave, Convex}` (decision 81); the port is now
  `add_quadratic`, `max_convolve(point/flat)` and `at(half)`. `at(c)` is
  O(c - lo + log n) and `max()` O(n): the treap keeps no subtree sums.

## Amortized slope-treap growth costs 1.37x -> 1.5x
- **Goal it hurts:** performance and control.
- **Ideal code:** `var dp = Concave.point(0)` with no capacity hint; the
  treap's doubling growth costs a few percent, as `std::vector` growth does.
- **Today:** the port calls `dp.reserve(n)`, as the matched C++ reserves its
  node pool. Without it, at n = 5e5 (best of 9, g++ -O2): 148.5 ms against
  133.6 ms with the reserve and 95.3 ms for the C++. `perf`: the vector's
  regrowth is 4.4% of cycles (about 6.5 ms copying nodes; `TreapNode` is
  trivially copyable, 56 B), and page faults go from 7,247 to 14,196
  (about 8 ms: each doubling faults in a fresh buffer while the old one is
  still live). glibc `MALLOC_TOP_PAD_` / `MALLOC_MMAP_THRESHOLD_` change
  nothing.
- **General fix:** shrink the node (`?I32` children and `I32` sizes would
  make it 48 B, see the 2.03x RSS friction above), which cuts both the copy
  and the faults; or grow node storage in chunks that are never moved.
  Owner: containers (node storage) / core (`I32`).
- **Severity:** low (one `reserve` line recovers it).
- **Narrowed (decision 122):** sizes and priorities are `0..2^31`, nodes
  48 B. Best of 9: 127.4 ms with `reserve` (1.40x the 90.9 ms C++), 138.3 ms
  without; bench/dp slope 1.35x. The matched C++ node is also 56 B and also
  reserved, so layout is not what is left. `perf` puts 26% of cycles in
  `push_tag` (split the tag into a tuple, then two `put` calls, each reading
  the child's left size) and 39% in `ins`, against the C++'s inlined
  `downdate`. Chunked never-moved storage would only remove the 11 ms
  no-reserve regrowth, not this gap, so it is not built. Next: a
  `?(0..2^31)` field packed in 4 bytes (codegen), and a `push_tag` that
  applies the split tag without the tuple round trip.
- **Tags pushed in place:** `split_val` and `ins` called `push_tag(i, f)`
  with `f` bound by `if let f = nodes[i].tag`. The body mutates the treap,
  so the tag is copied (correctly), and the copy's address then escaped into
  the out-of-line `push_tag` call, forcing it through the stack. `down(i)`
  now reads the tag and pushes it in one function. bench/dp slope 1.35x ->
  1.20-1.26x (two runs), under the 1.3x target. Returning the split tags as a
  tuple and destructuring them costs nothing: replacing it by hand in the
  emitted C++ left the time unchanged (127.7 ms both), so codegen is unchanged.
