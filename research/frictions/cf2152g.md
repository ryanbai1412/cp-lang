# cf2152g — Query Jungle

Rethought rather than translated: the original maintains the answer with a
hand-rolled top tree (about 500 lines of rake/compress machinery). The
observation that removes it: a monster needs its own path exactly when no
other monster lies in its subtree, i.e. when the next monster in preorder is
not its descendant (or there is none). So the answer is the number of
consecutive monster pairs in preorder that are not ancestor and descendant,
plus one, and a subtree flip is a range flip over preorder. A lazy segment
tree keeps, for the current monster set and for its complement, that count
and the first and last monster of the range; a flip swaps the two halves.

## The flipped-complement pattern is spelled out by hand
- **Where:** `cf2152g.cp`, lines 12–26 (`type Node = (now: Side, flipped:
  Side)` and the `Action` with its `Monoid`).
- **What felt wrong:** "maintain an aggregate under range complement" is a
  standard lazy-tree shape: keep the aggregate of the set and of its
  complement, and a flip swaps them. The port writes it from scratch: a pair
  type, a monoid that applies `join` to both components, an action with
  `id`, `compose: (f, g) => f != g` and an `apply` that swaps. Only `join`
  and the leaf are about this problem; the other ten lines are the pattern,
  and they would be written again verbatim for "count ones under range flip",
  "longest run under flip" and so on.
- **Goal it hurts:** express (the program should show the invariant, not the
  plumbing); accumulate.
- **Ideal code:**
  ```cp
  let side = Monoid<Side>(none_side, join)
  var st = LazySegTree<t.Pre, _>(Flip(side), t.reorder([V] v => leaf(v)))
  print(st.all.now.ends)
  ```
  where `Flip(m)` is a library action over `(now: T, flipped: T)` built from
  any monoid `m`.
- **General fix:** product monoids derived componentwise (`Monoid.pair(m, m)`
  or records of monoids, `design/spec/27-algebra-segtrees.md`) plus a small
  set of named library actions (`Flip`, `Assign`, `Add`) parameterised by the
  monoid they act on, written in user-level CP Lang so personal libraries can
  add their own.
- **Dream:** `dream/cf2152g.cp` lines 9–13 and 15: `Side` is a struct with its join, and `Flip(Side)` is the action.
- **Severity:** medium.
- **Status:** fixed: added `Flip<T>` (`Flip.of`) and `flip_action<T, M>(m)` in `std.lazy` plus capture-elided higher-order closure devirtualization in `cpl-codegen`; `cf2152g.cp` dropped from 387 to 280 tokens (1.27x of dream) and 35,469 to 30,720 B emitted with 0 `std::function` (`cpl explain`: 8 static direct, 0 dynamic).
- **Area:** ranges

## Lazy-tree monoid and action are emitted as `std::function`
- **Where:** `cf2152g.cp`, lines 21–26, as emitted: `compose` and `apply` are
  `const std::function<...>&` parameters of the action.
- **What felt wrong:** every push-down and combine goes through an indirect
  call on a 32-byte tuple. The port still beats the original on the max
  input (the original pays for its top tree), but the same abstraction cost
  makes `cf2165f` 1.6x slower than hand-written C++. Peak memory is 102 MB
  against the original's 57 MB on `n = q = 250,000`; I did not isolate how
  much is the tree layout and how much the `Rooted` tables, and narrowing
  `ends` to `0..=n` did not change it, which suggests the record field is not
  the cost.
- **Goal it hurts:** performance and control (seeing what allocates).
- **Ideal code:** unchanged.
- **General fix:** monomorphize monoids and actions whose operations are
  lambda literals or named functions, and have `cpl explain` show the node
  layout and the bytes per node of every segment tree.
- **Dream:** `dream/cf2152g.cp` line 15 (the fix is in what it compiles to).
- **Severity:** medium.
- **Status:** fixed: static closure lowering (`08e78a90`) elides all `Action`/`Monoid` `std::function` fields and parameters in `cf2152g.cp` (`cpl explain`: 7 static direct, 0 dynamic `std::function`).
- **Area:** core

## `x.first ?? y.first` for "the first present" reads like a default
- **Where:** `cf2152g.cp`, line 17: `(ends, x.first ?? y.first, y.last ?? x.last)`.
- **What felt wrong:** this worked, but I had to try it: whether `??` with an
  optional on the right yields an optional (`or` semantics) or demands a
  plain value is not stated in the cheat sheet, and the two readings differ
  in type. "First non-empty of two ranges" is also a monoid of its own
  (`First<V>` / `Last<V>`), which would have made `Side` a product of three
  library monoids and `join` only the ancestor correction.
- **Goal it hurts:** express (guessable semantics).
- **Ideal code:** `(ends, x.first or y.first, y.last or x.last)` or `Side`
  as a record of `Sum`, `First` and `Last` monoids.
- **General fix:** document `??` on optional right-hand sides (and test it),
  and ship `First`/`Last` monoids next to `max`/`min` so product monoids
  compose without custom joins.
- **Dream:** `dream/cf2152g.cp` line 13 (`x.first or y.first`).
- **Severity:** low.
- **Area:** core

## `Rooted` holds 64 MB for a 250,000-vertex tree; the original needs 56 MB in all
- **Where:** `cf2152g.cp` line 10: `Rooted(Graph.undirected(...), V.first)`.
- **What felt wrong:** the port peaks at 102 MB against the original's 57 MB
  on the max input. Logging `VmHWM` between statements of the emitted C++:
  9 MB after reading, 73 MB after `Rooted(...)`, 102 MB after the
  `LazySegTree` is built. The port can only shrink the tree's node
  (`ends: 0..=250_000` still emits `ll`, so it gains nothing); the rest is
  layout the port cannot reach:
  - `Rooted` eagerly computes and keeps `par`, `dep`, `far`, `sz`, `kid`,
    `heavy`, `top`, `tin` and `at`, with `dep`, `far` and `sz` as 64-bit
    although each is at most `V.count`, and `kid` a second
    `vector<vector<int>>` beside the adjacency it was built from; the build
    also holds a `seen`, an `order` and a 16-byte-per-entry DFS stack.
    This port uses only `is_anc`, `sub` and `reorder` (`tin` plus `sz`).
  - The `LazySegTree` build holds the leaf list, its reordered copy and an
    `optional` copy of that at once (29 MB for 2^19 nodes of 32 bytes).
- **Goal it hurts:** performance (values take the fewest bytes their types
  allow; you can see what allocates).
- **Ideal code:** unchanged.
- **General fix (trees area):** store `Rooted`'s per-vertex counts in the
  width their bound proves (`dep`, `sz` and `tin` are in `0..=V.count`),
  free the build scratch before returning, and compute the heavy-path
  arrays and `far` on first use. **(Range structures area):** build the
  tree in place from the leaf list instead of through two copies. **(Codegen
  lane):** honour a ranged tuple field's width in the emitted tuple.
- **Dream:** `dream/cf2152g.cp` lines 7 and 15 (same calls; the fix is in
  their layout).
- **Severity:** medium.
- **Area:** trees

## Measurements
- **Contestant-written tokens:** port 277 vs original 1,003 (problem code
  from `my_top_tree_node` on; 3,902 with the top-tree template): 0.28x. Dream: 233.
- **Max input (`n = q = 250,000`, deep near-path tree, random flips):**
  original 1.00–1.36 s, 57,472 KB (it recurses on the tree and segfaults under an
  8 MB stack; measured with an unlimited stack as on Codeforces); port
  0.47–0.60 s, 86,136 KB (102,140 KB before main lowered static closures without
  `std::function`; also passes under an 8 MB stack); outputs agree.
- **Gate:** `gate.sh cf2152g 150` passes (1 sample, 150 random cases).
- **Emitted C++:** 31,022 bytes.
