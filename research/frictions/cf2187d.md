# cf2187d — Cool Problem

Before the first `?` the walk is fixed, giving `c0` and the partial sum `f`.
After it, every completion ends at one of a line of canonical strings
`0 0^k 1^(m-k)` / `1 0^k 1^(m-k)`, whose sums are closed forms. Tracking the
two parity offsets `p0, p1` through the rest of the string, each later `?`
adds an optional even gap, so the reachable end positions are `2i + p` with
`i` a subset sum of the half-gaps. The half-gaps sum to at most `n`, so a
bitset knapsack is enough; the original instead takes `exp(log(prod (1 + a x^g)))`
over a 1,400-line power-series template with random `a` to test which
coefficients are nonzero.

## The obvious bitset knapsack is ten times slower than the original

- **Where:**
  ```
  for g in Half if g.to_idx > 0:
      let pairs = (copies[g] - 1) / 2
      if pairs > 0:
          copies[g] -= 2 * pairs
          if let g2 = Half.try_at(2 * g.to_idx): copies[g2] += pairs
      for _ in 0..copies[g]: reach.union(reach.shifted(g.to_idx))
  ```
- **What felt wrong:** the first version was the knapsack step the
  `Bitset.shifted` doc suggests, once per gap:
  `for g in half_gaps: reach.union(reach.shifted(g))`. On the all-`?` max
  input that is 99,999 copies of the same weight and took **0.75 s** against
  the original's **0.08 s** (each step also allocates a fresh `Bitset` for
  `shifted`). The fix is the folklore carry (three copies of `g` reach what
  `g` and `2g` reach, so pairs move up to `2g`), which leaves O(sqrt n) items
  and brings the port to **0.13 s**. Six lines and a proof comment for a
  standard building block, and the natural code is the slow one.
- **Goal it hurts:** performance (the obvious way is not the fast way),
  express.
- **Ideal code:**
  ```
  let reach = subset_sums(gaps, upto: rest.len)   // Bitset, carries equal weights
  ```
- **General fix:** a `subset_sums(weights, upto:)` in the stdlib
  (multiset or `Bag` of weights in, `Bitset<0..=upto>` out), documented
  O(upto * sqrt(sum) / 64), doing the carry; plus an in-place
  `reach |= reach << g` that does not allocate, so hand-written knapsacks
  with extra structure stay fast.
- **Severity:** high
- **Status:** fixed: `Bitset<D>.subset_sums(weights)` (with binary-carry grouping and in-place `shift_or`) replaces the hand-rolled carry loop in `proto/ports/ecnerwala/cf2187d.cp`; max all-`?` input (`n = 100,000`) dropped from `0.13 s` to `0.03 s` (4.3x faster than old port, 2.7x faster than C++ original's `0.08 s`).
- **Dream:** `proto/ports/ecnerwala/dream/cf2187d.cp` lines 12, 16, 17.

## Arrays over a negative range need a named domain and a wrapper at every index

- **Where:** `domain Pos = -m..=m + 1`, `var end_f: [Pos]Int = 0`,
  `end_f[Pos(pos)] = ...`, `end_f[Pos(2 * i.to_idx + p)]`; and likewise
  `domain Half = 0..=m`, `copies[Half(...)]`, `reach.add(Half(0))`,
  `g.to_idx`, `Half.try_at(2 * g.to_idx)`.
- **What felt wrong:** the natural `var end_f: [-m..=m + 1]Int = 0` checks
  but `cpl run`/`cpl build` reject it (`E0501: ... an array dimension that
  starts at anything but a number yet`). Naming the range is fine, but the
  positions here are arithmetic (`2i + p`, `2g`, `-k`), so every access
  converts Int -> domain -> Int. Half-gap weights are numbers you add and
  double, not an index space, yet `Bitset<D>` forces them into one. Nine
  conversions in a 50-line program, none of which catches a bug.
- **Goal it hurts:** express, revise.
- **Ideal code:**
  ```
  let end_f: [-m..=m + 1]Int = [ ... ]
  print(sum(Z(v) for v in {end_f[2 * i + p] for i in reach for p in [p0, p1]}))
  ```
- **General fix:** let an anonymous integer range (any bounds) be an array
  dimension in every backend (the checker already accepts it), and let a
  range-typed `Int` index such an array directly: the range is the proof,
  as `design/spec/21-index-spaces.md` allows for plain integer ranges.
  `Bitset` over an integer range should take and yield `Int`.
- **Severity:** medium
- **Dream:** `proto/ports/ecnerwala/dream/cf2187d.cp` lines 12, 19-23, 24.

## A Bitset is not iterable

- **Where:** `for i in reach.each():`
- **What felt wrong:** `for i in reach:` fails with
  `E0302: a for can't walk over a Bitset<Half_0>`, while `Set`, `Subset<D>`
  and domains all iterate directly. The method name had to be found in
  `stdlib/bitset.cp`.
- **Goal it hurts:** guessable APIs.
- **Ideal code:** `for i in reach` (and `{... for i in reach ...}`).
- **General fix:** every container with an `each() -> yields T` is
  iterable by `for`; one protocol, not a per-type list.
- **Severity:** low
- **Status:** fixed: any struct with `each(self)` (including `Bitset<D>`) is directly iterable in `for i in reach:` (decision §66.1); `proto/ports/ecnerwala/cf2187d.cp` now writes `for i in reach:`.
- **Dream:** `proto/ports/ecnerwala/dream/cf2187d.cp` line 24.

## Splitting at the first `?` uses a sentinel and repeats the walk

- **Where:** `let q = s.find('?') ?? s.len` ... `if q == s.len:`, and the
  recurrence `if ch == '0': x + c0 else: y - c0` written inline in the head
  loop while the closed forms for the tail encode it again.
- **What felt wrong:** `?? s.len` turns "no `?`" into a sentinel that is
  then compared again two lines later; the `if let` form instead forces the
  head walk into one branch and a duplicate into the other (the first draft
  did exactly that). A string split that returns an optional pair, and a
  `scan` with an explicit seed for the walk, say it once.
- **Goal it hurts:** express, hard to get wrong (sentinel).
- **Ideal code:**
  ```
  fn step(c: Int, ch: Char) -> Int = if ch == '0': x + c else: y - c
  let walk = s.scan(step, from: 0)
  guard let (head, rest) = s.split_first('?') else: return print(Z(walk.sum()))
  ```
- **General fix:** `split_first(sep) -> ?(Str, Str)` on sequences, and a
  seeded `scan(f, from:)` (`design/spec/22-sequences.md` scan family).
- **Severity:** low
- **Dream:** `proto/ports/ecnerwala/dream/cf2187d.cp` lines 7-10.

## What worked

- `(p0, p1) = (p1, p0)` and `(p0, p1) = (p0 + 1, p1 - 1)` keep the two
  offsets as one state.
- `Set<Int>` plus `sum(Z(v) for v in cool)` is the dedupe-and-sum in two
  lines; `Z(v)` of a negative `Int` reduces correctly.
- No power series: the editorial-level observation (half-gaps sum to at
  most `n`) replaces the original's randomized `exp`/`log` with a
  deterministic knapsack.
