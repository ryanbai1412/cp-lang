# cf2237h — H. Slime and Queries

The editorial idea: each query paints the path `cur -> c` with timestamp `t_now`. Every vertex on the path whose previous paint was `t_old` demands 1 unit of slime from the newest non-empty supply bucket `<= t_old`; unmatched demand increases `tot_ans`, and all matched slime moves into bucket `t_now`.

## No interval partition map (`IntervalMap<D, T>`) in stdlib (owned by containers area lane)
- **Where:** `proto/ports/ecnerwala/cf2237h.cp` lines 17-46, 59-60:
  ```cp
  struct PaintMap:
      segs: Map<Int, (r: Int, t: Time)>
      fn split(mut self, x: Int): ...
      fn assign(mut self, l: Int, r: Int, t_now: Time, mut out: List<(t: Time, w: Int)>): ...
  ```
- **What felt wrong:** Hand-rolling an ODT / Chtholly tree (`PaintMap` with manual `split`, `remove`, and initial run-length compression) accounts for ~30 lines and forces leaving the nominal `tree.Pre` domain via `.ord` to store raw `Int` endpoints.
- **Goal it hurts:** express, hard-to-get-wrong
- **Ideal code:**
  ```cp
  var paint = IntervalMap<tree.Pre, Time>(Time(1))
  for v in init: paint.assign(tree.pos(v)..=tree.pos(v), Time(2))
  ...
  var chunks = [
      (t, w: r.len)
      for (range, _) in tree.chains(cur, c)
      for (r, t) in paint.assign(range, t_now)
  ]
  ```
- **General fix:** `IntervalMap<D, T>` in stdlib (owned by the containers area lane) over any domain `D`, supporting `assign(range: Range<D>, val: T) -> yields (range: Range<D>, old: T)` and automatic adjacent-merge.
- **Dream:** `dream/cf2237h.cp` lines 13-14, 26-30.
- **Severity:** high
- **Status:** fixed: the port paints with `IntervalMap.from` over `tree.Pre` and `paint.assign(range, t_now)` per heavy chain; `PaintMap` and its run-length setup are gone.

## No dynamic tree (`LinkCutTree` / `TopTree`) in stdlib forces an extra log factor
- **Where:** `proto/ports/ecnerwala/cf2237h.cp` lines 13, 59-63:
  ```cp
  let tree = Rooted(Graph.undirected(edges), V.first)
  ...
  for (range, _) in tree.chains(cur, c):
      paint.assign(range.lo.ord, range.hi.ord, t_now, mut chunks)
  ...
  sort(mut chunks, by: x => desc(x.t))
  ```
- **What felt wrong:** Without a dynamic tree (`LinkCutTree` / `TopTree`), HLD (`tree.chains`) + `Map` ODT costs $O((n + q \log n) \log n)$ and re-sorts `chunks` per query, running 1.69x slower than the C++ Top Tree on max input (0.49 s vs 0.29 s).
- **Goal it hurts:** performance, express
- **Ideal code:**
  ```cp
  // LinkCutTree / TopTree path-assign returning color runs in O(log n) amortized
  ```
- **General fix:** Add a generic `LinkCutTree` / `TopTree` to stdlib/local-lib for dynamic trees and $O(\log n)$ amortized path-assign queries.
- **Dream:** `dream/cf2237h.cp` lines 26-33 (removes HLD + sort log factor if backed by dynamic tree).
- **Severity:** medium
- **Status:** partly fixed: `std.tree.LinkCut` gives link, cut and ordered path folds in amortized O(log n); assigning a colour to a path and reading back its runs is not in it yet, so this port stays on `chains` + `IntervalMap`. A path-paint dynamic tree (access colouring: one run per preferred-path switch, amortized O(log n)) would give the dream, but it is held until a second problem needs it; `LazyLinkCut`'s generic `Action` cannot report uniform runs.

## `IntervalMap.assign` returns a fresh `List` per call (owned by containers area lane)
- **Where:** `proto/ports/ecnerwala/cf2237h.cp`, the chain loop:
  ```cp
  for (range, _) in tree.chains(cur, c):
      for (r, t) in paint.assign(range, t_now): chunks.push((t: t, w: r.len))
  ```
- **What felt wrong:** the obvious code is slower than the hand-rolled `PaintMap` it replaced: 1.75 s vs 1.55 s on the generator at S = 24999 (original 1.06 s). Each `assign` allocates a result list and rebuilds every overwritten run as a `Range<D>` through `D.nth`, where the old code pushed `(t, w)` into one reused list.
- **Goal it hurts:** performance
- **General fix:** let `assign` accept an optional zero-alloc callback `on_old: (Range<D>, T) -> () = (_, _) => ()` (devirtualized to a template functor by `cpl-codegen`) with a single-run fast path so no list is allocated and single-segment paints avoid redundant `split`/`D.nth`/`remove` work.
- **Severity:** medium
- **Status:** fixed: `IntervalMap.assign` takes `on_old: (Range<D>, T) -> () = (_, _) => ()` with zero heap allocation and a single-run fast path; `cf2237h` calls `paint.assign(range, t_now, on_old: (r, t) => chunks.push((t: t, w: r.len)))`. On deep binary tree max input ($n = 100{,}000, m = 50{,}000, q = 100{,}000$), `cf2237h` dropped from **1.66 s** to **1.26 s** median user time (24% faster, emitted C++ **36,437 B**); on a matched-algorithm ODT benchmark ($N = 100{,}000, Q = 300{,}000$), `IntervalMap` runs in **0.15 s** vs **0.13 s** matched C++ `std::map` (**1.15x**).

## Discarded `Map.remove` still costs a lookup and a copy (owned by containers area lane)
- **Where:** `stdlib/interval.cp`, `IntervalMap.assign`: `let _ = segs.remove(lo)` and the right-merge `segs.get(new_hi)` then `segs.remove(new_hi)`.
- **What felt wrong:** after the single-pass `assign`, cf2237h is still 1.8-1.9x the original: 1.07 s vs 0.59 s (seed 1) and 0.60 s vs 0.34 s (seed 2) at S = 24999, identical output. perf: `cpl::map_get` 13.5%, `Rb_tree` erase 11%, `Rooted.chains` 4%. A discarded `remove` emits `map_get(segs, k)` and then `segs.erase(k)`: two lookups plus a value copy where C++ does one `erase`.
- **Goal it hurts:** performance
- **General fix:** lower a discarded `Map.remove` to a bare `erase`, and let a lookup followed by a write or remove of the same key reuse the iterator.
- **Severity:** medium
- **Status:** open, sent to containers.
