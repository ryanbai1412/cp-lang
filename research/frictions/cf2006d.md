# cf2006d — Iris and Adjacent Products

The editorial: the best order alternates large and small values, so a
window of length `L` is fixable without changes iff, for every
`i ≤ √k`, the values too big to sit beside anything above `i` (those
`> k / (i + 1)`) are matched by values `≤ i`, counting at most `⌊L/2⌋` of
each; one change fixes two mismatches. A value `b > √k` matters only
through `k / b`, so both sides are histograms over `1..=√k`, kept per
window by Mo's algorithm, and each answer is a max over the two prefix
sums. O((n + q)√n + q√k).

## Mo's algorithm has no driver
- **Status:** resolved (`std.mo.mo(queries, add:, remove:, answer:)` added; `cf2006d.cp` and `cf2129e.cp` migrated).
- **Where:** `cf2006d.cp`, lines 12, 16–23:
  ```cp
  let windows = [d.l..=d.r for d in days]
  ...
  var cur = P.first..P.first
  for x in mo_order(windows):
      for (pos, entering) in mo_steps(cur, windows[x]):
          ...
      cur = windows[x]
  ```
- **What felt wrong:** `mo_order` and `mo_steps` are the two halves of Mo,
  and every user glues them with the same five lines: an empty starting
  window, a loop over the order, a step loop, and the window update. The
  empty window is spelled `P.first..P.first`, which is unguessable, and
  forgetting `cur = windows[x]` re-adds every position on the next query.
  Answers are scattered into `ans[x]` by hand.
- **Goal it hurts:** express; hard to get wrong (state leakage).
- **Ideal code:** `days.mo(step: (i, d) => ..., answer: w => ...)`
  returning the answers in query order.
- **General fix (seq):** a `mo(windows, step:, answer:)` driver over
  `mo_order` and `mo_steps` that owns the current window, with `d` as
  `+1`/`-1` so add and remove are one closure.
- **Dream:** `dream/cf2006d.cp` lines 13–17.
- **Severity:** high.
- **Area:** seq

## No integer square root
- **Status:** resolved (`isqrt(k)` is in the prelude and used in `cf2006d.cp`).
- **Where:** `cf2006d.cp`, lines 8–9:
  ```cp
  var root = 1
  while (root + 1) * (root + 1) <= k: root += 1
  ```
- **What felt wrong:** `⌊√k⌋` is the threshold the whole solution is built
  on. The stdlib has `sqrt` only for power series; a float `sqrt` would be
  off by one near squares. So it is a loop, O(√k) per test.
- **Goal it hurts:** express; hard to get wrong (boundaries).
- **Ideal code:** `k.isqrt`.
- **General fix (math):** `isqrt` (and `icbrt`) on `Int`, exact.
- **Dream:** `dream/cf2006d.cp` line 8.
- **Severity:** medium.
- **Area:** math

## Levels are integers, not a domain
- **Where:** `cf2006d.cp`, lines 10, 13–14, 25:
  `var small: [root + 1]Int`, `small[at] += d`, `for i in 1..=root`.
- **What felt wrong:** both histograms are over the same index space
  `1..=√k`, but it is computed at run time, so it is `[root + 1]` with an
  unused slot 0, and nothing ties `at` (from `b[i]` or `k / b[i]`) to it.
  A runtime-valued domain (`domain Level = 1..=k.isqrt`) works for input
  sizes, but the loop above can't produce one before it is declared.
- **Goal it hurts:** hard to get wrong (wrong index space).
- **Ideal code:** `domain Level = 1..=k.isqrt` and `var small, big: [Level]Int = 0`.
- **General fix (math):** follows from `isqrt`; plus multi-name
  declarations `var small, big: [Level]Int = 0`.
- **Dream:** `dream/cf2006d.cp` lines 8, 10.
- **Severity:** medium.
- **Area:** core

## A two-way tag is a record with a Boolean
- **Where:** `cf2006d.cp`, lines 10, 20–22:
  ```cp
  let level = [P] i => if b[i] <= root: (small: true, at: b[i]) else: (small: false, at: k / b[i])
  ...
  if is_small: small[at] += d else: big[at] += d
  ```
- **What felt wrong:** each position is either a small value or a big
  value's need; that is a sum type, and the record with a flag lets
  `at` be read without asking which side it is on.
- **Goal it hurts:** hard to get wrong; express.
- **Ideal code:** `Small(Level(b))` / `Big(Level(k / b))` and a `match`.
- **General fix (core):** data-carrying enum variants with `match`.
- **Dream:** `dream/cf2006d.cp` lines 9, 14.
- **Severity:** medium.
- **Area:** core

## The answer is a running max of two prefix sums written as a loop
- **Where:** `cf2006d.cp`, lines 24–28.
- **What felt wrong:** "the worst level" is `max` over the paired prefix
  sums of `big` and `small`; it is three mutable accumulators instead, and
  `Int(b)` for the parity term.
- **Goal it hurts:** express.
- **Ideal code:** `zip(big.prefix_sums(), small.prefix_sums()).max(...) ?? 0`.
- **General fix (seq):** a lazy `prefix_sums()` method on `[D]T`; `max`
  with a key; `.int` on `Bool`.
- **Dream:** `dream/cf2006d.cp` lines 15–16.
- **Severity:** low.
- **Area:** seq

## Off-by-one in the window length hid behind the virtual element
- **Where:** `cf2006d.cp`, lines 15, 28: `small[1] = 1` and
  `cur.len + 1 > need + have`.
- **What felt wrong:** the original adds a virtual `1` to the small side
  and compares against the window length plus one; my first port used
  `cur.len` and passed the sample, failing only on random tests. Nothing
  in the language helps here, but it is a trap worth noting: the `+ 1`
  and the virtual element are one fact written in two places.
- **Goal it hurts:** hard to get wrong (boundaries); revise.
- **Ideal code:** name it once (a `small[1] += 1` the window length also
  counts), as the dream does on lines 11 and 16.
- **General fix:** none in the language; recorded for the bug corpus.
- **Dream:** `dream/cf2006d.cp` lines 11, 16.
- **Severity:** low.
- **Area:** none

## The port runs 2.1x the original on the max input
- **Status:** resolved (`std.mo.mo` runs in-place pointer moves with 0 `std::function` and 0 step-list allocation, bringing `cf2006d` from 2.1x down to 1.34x: 271.8 ms vs 202.4 ms on n = q = 10^5, k = 10^6).
- **Where:** `cf2006d.cp`, lines 18–28.
- **What felt wrong:** on the max input (n = q = 10^5, k = 10^6) the port
  takes 0.43–0.47 s against the original's 0.21–0.22 s. Replacing
  `mo_steps` (which builds a `List` of steps per query) with four
  hand-moved window loops brings it to 0.35 s, so about 0.1 s is the step
  list; the rest is in the per-query level scan and the record lookup,
  not yet profiled further. The readable stdlib path is the slow one.
- **Goal it hurts:** performance (max at most 1.5x).
- **Ideal code:** `days.mo(step:, answer:)` compiled to in-place pointer
  moves.
- **General fix (seq, codegen):** make `mo_steps` a generator (no list),
  or the `mo` driver above, so the steps inline into the caller.
- **Dream:** `dream/cf2006d.cp` lines 13–17.
- **Severity:** high.
- **Area:** codegen

## Top-level `namespace prog` globals block register promotion and if-conversion in Mo callbacks
- **Where:** `bench/ranges/mo.cp` (`var freq: [vmax]Int = 0; var distinct = 0`) and Mo ports (`cf2006d.cp`, `cf2129e.cp`).
- **What felt wrong:** Matched `bench/ranges/mo.cp` runs in 112.7 ms vs 43.9 ms for `bench/ranges/mo.cpp` (2.57x) despite `mo_order` being faster than C++ (10.7 ms vs 13.5 ms, 0.79x), `add`/`remove` inlining at all 4 call sites, and zero `cpl::pos` checks. Moving `a`/`freq`/`distinct` to file-scope globals in `mo.cpp` jumps C++ itself from 43.9 ms to 106.5 ms (2.43x), leaving `std.mo.mo` at 1.06x vs global C++. Under C++11, GCC cannot hoist a file-scope global `distinct` into a register or if-convert `if (freq[v] == 0) distinct += 1` into branchless `adc`/`cmov` (speculative stores to shared globals are forbidden), turning a 1-cycle register `adcl` into a 50%-mispredicted branch + memory RMW on all 26.4M steps. Even inside a local `fn run()`, passing `[&distinct]` into a non-inlined `m1_mo` exposes `ll&` that aliases `std::vector<ll> freq`.
- **Goal it hurts:** performance (p50 ≤ 1.1x matched C++).
- **Ideal code:** top-level `var`s that do not escape `solve()` stay local to `solve()`, and small/template driver functions (`mo`) are emitted `inline` so GCC sees local accumulators never alias `freq`.
- **General fix (codegen):** emit non-escaping top-level `var`s as locals in `solve()` (or `static` with `inline` drivers) so scalar accumulators promote to registers and if-convert across callback loops.
- **Severity:** high.
- **Area:** codegen
