# cf2129f1 — F1. Top-K Tracker (Easy Version)

## `cpl fmt` strips the space between `where` and `(` in comprehensions
- **Where:** `proto/ports/ecnerwala/cf2129f1.cp` (initial draft line 49: `[v for v in 1..=n where (masks[v - 1] >> q) % 2 == 1]`):
  `cpl fmt` reformatted it to `where(masks[v - 1] >> q) % 2 == 1`, gluing the keyword `where` onto the opening parenthesis.
- **What felt wrong:** `where` is a clause keyword, not a function call; gluing `where(` makes the filter expression look like a call to `where(...)` and hurts readability. (Using `masks[v].bit(q)` avoided the leading parenthesis in the final version.)
- **Goal it hurts:** express
- **Ideal code:**
  ```cp
  let vals = [v for v in 1..=n where (masks[v] >> q) % 2 == 1]
  ```
- **General fix:** In `cpl-fmt`, always emit a space after the `where` keyword before any expression, including parenthesized expressions.
- **Severity:** medium

## `L0414` flags `for b in a + 1..order.len` as bounds-checked even when `a in 0..order.len`
- **Where:** `proto/ports/ecnerwala/cf2129f1.cp` lines 38-42 (initial draft used triangular loops `for a in 0..order.len: for b in a + 1..order.len: for c in b + 1..order.len:` indexing `order[a], order[b], order[c]`).
- **What felt wrong:** `cpl lint` emitted `warning[L0414]` on `order[b]` and `order[c]` because the range proof did not chain `0 <= a < order.len` into `0 <= a + 1 <= b < order.len`. To keep 0 lint warnings without introducing a dummy domain for a 29-element temporary list, the port had to iterate `for x in order: for y in order: for z in order: if x < y and y < z:` (6x more iterations, though tiny for 29 elements).
- **Goal it hurts:** express, performance
- **Ideal code:**
  ```cp
  for a in 0..order.len:
      for b in a + 1..order.len:
          for c in b + 1..order.len:
              if try_add([order[a], order[b], order[c]]): break
  ```
- **General fix:** Propagate `lo >= 0` from `a in 0..xs.len` to `b in a + 1..xs.len` in the bounds prover so triangular pair/triple index loops (`0 <= a < b < c < xs.len`) are proven in-bounds without lint warnings.
- **Severity:** medium

## No `@!once` / shared precomputation with `@!multitest` (and no multi-level `break` out of nested loops)
- **Where:** `proto/ports/ecnerwala/cf2129f1.cp` lines 37-46:
  ```cp
  var added = false
  for x in order:
      for y in order:
          for z in order:
              if not added and x < y and y < z and try_add([x, y, z]):
                  added = true

  let t: 1..=40 = read()
  for _ in 0..t:
  ```
- **What felt wrong:** Two small frictions in the same file:
  1. Because the 845-mask table is shared across all `t <= 40` test cases, `@!multitest` cannot be used and the test loop must be written manually.
  2. Finding the first valid triple in a nested loop needs either a helper function or a boolean `added` flag to simulate a labeled `break`.
- **Goal it hurts:** express
- **Ideal code:**
  ```cp
  @!interactive
  @!multitest
  // with `@!once` for shared precomputation and `break 'outer` for nested search
  ```
- **General fix:** Allow `@!once` (or top-level pre-test bindings) alongside `@!multitest`, and ensure labeled `break` is ergonomic for nested search loops.
- **Severity:** low
