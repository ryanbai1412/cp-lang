`vector<vector<int>> adj(n + 1)` filled by `adj[u].push_back(v)` as each edge is read is how C++ stores a graph, and `[[] for _ in 0..=n]` with `adj[u].push(v)` is its literal translation: `n + 1` separate lists, a wasted slot 0, and vertex numbers that are plain `Int`s. CP Lang reads the whole edge list at once, `let es: [E](u: V, v: V) = read()` with `domain V = 1..=n` and `domain E = 0..m`, and `std.graph` builds the graph from it: `Graph.undirected(es)` stores both arcs of each edge, `Graph.directed(es)` one, in a single compact block that keeps input order. Every vertex is a `V`, so a vertex from another index space, or a `0` from a 1-based input, is a type error rather than a silent read. `bfs`, `dijkstra`, `components` and the rest take the graph as it is. A graph that keeps growing after input stays a `[V]List<V>`.

The lint fires on a `var` list of lists (or `[D]List<..>`) started empty that a `for` loop over the edge count fills from one read of both ends, nothing else in the loop: `adj[u].push(v)` alone, `adj[u].push(v)` then `adj[v].push(u)`, or `adj[u].push((v, w))` with a weight read alongside. Its fix, declared by `@lint` on `Graph.directed` and `Graph.undirected` in `std.graph`, declares `domain V` over the ends' range, reads the edges at once and builds `Graph.directed(es, keep: arc => arc.to)` (`Graph.undirected` for both pushes, `(arc.to, arc.w)` for a weight), so `adj[u]` still lists `u`'s neighbours.
