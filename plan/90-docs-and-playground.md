# 9. Documentation site, learning resources, playground

Status: proposed; superseded for the website rebuild by `site/` (start at
`site/README.md`) where they disagree. The user asked for "a beautifully
designed docs site" and "some sort of online playground where you can
just solve lots of cp problems". This doc says what it is and what it
should feel like.

The audience is a strong C++ competitor. They already know the algorithms,
so every page answers one question: "what do I write here instead of what I
write in C++, and why is it better?" Nothing explains what a segment tree is.

## 9.1 What the site contains

The site has six sections. Each is described here by what a reader does
with it.

### The tour (one afternoon)

A single long page, about 30 runnable examples, that takes a C++ competitor
from zero to solving a Div 2 C. It follows the 1.1 tour but goes slower,
and every example has a Run button and an editable box. The order is
fixed, because each step uses the one before:

1. A whole program: read, compute, print. The file is a function body.
2. `let`, `var`, `Int`, range types. Why `1..=2e5` is a type.
3. Domains. Indexing `[V]Int` with an `E` fails, and the reader sees the
   error.
4. Optionals instead of `-1` and `INF`.
5. Loops, reductions and sequence views (`runs`, `pairs`, `windows`).
6. Functions: parameters borrow, `mut` at both ends, `.copy()`.
7. Structs, records and enums with `match`.
8. Operation values: `SegTree<V, Int>(Max<Int>)`, `sort(xs, by: ...)`.
9. `@multitest`, `static let`, top-level `return`.
10. The tools: `cp run d i1`, `--trace`, `cp stress`, `cp build`.

Each step ends with a "C++ habit" box that shows the C++ the reader would
have written and the bug it invites:

```
// C++ habit
vector<long long> pre(n + 1);
for (int i = 0; i < n; i++) pre[i + 1] = pre[i] + a[i];
long long sum = pre[r] - pre[l - 1];      // did you mean pre[r + 1]?

// here
var pre: [V.cuts]Int = 0
for v in V: pre[v.after] = pre[v.before] + a[v]
let sum = pre[r.after] - pre[l.before]   // pre[r] doesn't compile
```

### The guide (one chapter per idea)

About 15 chapters, each 10-20 minutes of reading, each built around two or
three real problems:

- Index spaces: domains, bounds, derived domains, `compress`, the escape
  hatches, and when to stay with `Int`.
- Absence and failure: `?T`, `??`, postfix `?`, `do:` blocks, why there are
  no sentinels.
- Ownership without pointers: owning variables, borrowing parameters,
  handles and pools for trees and tries, `defer` and rollback.
- Generic code: traits vs operation values (the one-line rule), laws, and
  writing your own `SegTree` that is as fast as the stdlib one.
- Iteration: generators, `Iter` vs `Iterator`, adapters, sequence views,
  reductions.
- Program structure: program and library files, multitest, `static let`,
  parts and `@brute`, symmetry runs.
- Input and output: typed reads, input types, interpolation, interactors.
- Performance: reading `cp explain`, bytes per element, when checks remain
  and how to remove them, `unchecked:`.
- Debugging: the HTML trace, snapshots, `cp stress`, `cp locate`.
- Your own library: `lib/`, versions, pinning, upgrades.

### The reference

The language spec, generated from plan docs 1.2-1.8 and kept in the same
repository as the compiler. Every rule links to the diagnostic codes that
enforce it, and every diagnostic page links back to its rule. A rule
without a test is a CI failure.

### The stdlib reference

Generated by `cp doc` (doc 4b). Every item shows:

- its signature with the bounds written out;
- time complexity and memory per element (`SegTree<V, Int>`: 16 bytes per
  position);
- one example that runs as a test;
- a "C++ equivalent" line, such as `Fenwick` vs a hand-written BIT;
- the source, one click away, since the stdlib is ordinary code (G8).

### The error index

One page per diagnostic code: the message, a minimal program that triggers
it, the fix, and why the rule exists. The compiler prints the URL in every
message (`see: cp.dev/e/E0412`). This is also the error-message gallery the
golden tests check (doc 8).

### The cookbook

About 100 classic techniques, each with the user's original C++ next to
the port, from the validated corpus ports. Examples: prefix sums on bounds,
two pointers with `sliding`, Dijkstra with optionals, Euler tour with a
fresh `Pre` domain, rollback DSU with `defer`, digit DP with `@memo`,
offline queries with `sort` and `runs`. Each recipe says what the port
removed: lines, sentinels, `+1` shifts, manual resets.

## 9.2 What it looks like

- **Fast and static.** Pages are plain HTML generated at build time; the
  WASM compiler loads only when a code block is focused.
- **Live code blocks.** Hovering any identifier in any example shows its
  type and proven range, rendered by the same compiler as the LSP. Errors
  in edited examples appear inline, exactly as in VS Code.
- **Run in place.** Each block runs in the browser interpreter, with a
  "trace" link that opens the HTML walkthrough for that example.
- **Search** across the guide, reference, stdlib and error index, with
  keyboard navigation (`/` to search, `j`/`k` to move).
- **Light and dark themes,** one typeface for prose and one for code, and
  the same syntax colors as the VS Code extension.
- **Versioned.** Every page shows the compiler version it documents, and
  old versions stay available, since old solutions pin old versions.

## 9.3 The playground

### The editor

A browser editor with the WASM build of the compiler:

- diagnostics, hover, completion and formatting as you type, all on the
  client;
- debug runs in the interpreter, with the input boxes `i1`-`i5` matching the
  local workflow;
- the HTML trace, opened beside the code;
- cost warnings (TLE, MLE, overflow) against the problem's limits;
- a "show C++" pane with the bundled output and its size against 64 KB.

### Learning by solving

The fastest way to learn the language is to solve problems in it, so the
playground is mostly a problem set:

- **The learning path:** about 50 short problems, each teaching one
  feature. Problem 12 can only be solved cleanly with `V.cuts`; problem
  20 needs `runs`; problem 31 needs an operation value. Each has a hint that
  points to the guide chapter, and after an accepted submission it shows a
  model solution in the idiomatic style.
- **The classics:** about 500 standard problems (CSES-style, either with
  permissive licenses or written for this site), with hidden tests,
  checkers and interactors.
- **Translate a C++ solution:** paste C++, get a `cp port` draft
  (doc 10), then fix the marked places. This is the on-ramp for people with
  a big C++ library in their heads.

Per problem: the statement, samples, a submit button, the verdict with
per-test time and memory, past submissions, and an editorial written in
the language.

### The judge

Native runs use a sandboxed judge: the bundled C++ is
compiled with the problem's judge profile and run under seccomp with time,
memory and output limits. Verdicts match what a real judge would give, so
"accepted here" means "accepted there".

### Sharing

A share link stores the code, the inputs and optionally the trace. Opening
it shows the program with the walkthrough beside it, which makes it the
easiest way to ask "why is this wrong?".

## 9.4 How it is built and kept honest

- The site is generated from the repository: guide and tour are Markdown
  with runnable blocks, the reference comes from the spec, the stdlib and
  error pages from `cp doc` and the diagnostic registry.
- **Every code block is a test.** CI runs every example and checks its
  printed output or its expected error. A docs example that drifts from the
  compiler fails the build.
- Hover data in static pages is produced at build time, so the site works
  without JavaScript; live editing needs the WASM bundle.
- The playground's problem set lives in a separate repository with tests,
  checkers and model solutions, and is validated on every release like the
  corpus.

## 9.5 Hosting

Building the site and playground locally (`cp docs serve`) is part of the
plan. Publishing anything goes through an official deploy path and needs the
user's decision; nothing gets published without it.

## 9.6 Exit criteria

- A C++ competitor who has never seen the language solves a Div 2 C in it
  after the tour, without reading anything else.
- Every diagnostic has an error-index page with a runnable example.
- Every stdlib item has complexity, memory per element and a tested
  example.
- Every code block on the site passes CI.
