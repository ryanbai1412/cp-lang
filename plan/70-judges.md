# 7. Judges and submission

Status: profiles, selection and the profile matrix are built (0.2.2);
the rest of this chapter is proposed. Goal 5 (dependable submission):
one C++17 file the named judge accepts and runs as it ran here.

## 7.1 Judge profiles

A profile describes one judge (`crates/cpl-judge`): the compiler and the
flags the judge builds with, its platform, the stack it gives, the longest
source it accepts, whether it has `__int128`, and where each fact comes
from. Built in: `generic` (the default: `g++ -std=c++17 -O2`, 8 MB stack,
64 KB), `codeforces`, `atcoder`, `cses`, `icpc` (DOMjudge's defaults),
`kattis` and `dmoj`. `cpl judges` lists them and marks the one a build uses.

The judge is chosen by `cpl build --judge <name>`, else the file's
`// judge: <name>` line, else `judge = "<name>"` under `[judge]` in the
nearest `cp.toml`. A `[judge.<name>]` table changes a profile's fields or,
with `extends`, adds one:

```toml
[judge]
judge = "school"

[judge.school]
extends = "icpc"
title = "School judge"
stack_mb = 64            # or "unlimited"
source_kb = 100
flags = ["-std=c++17", "-O2"]
os = "linux"             # or "windows"
int128 = false
```

What a profile changes today:

- The header names the judge, its command and its stack.
- Deep recursion gets a 256 MB stack of its own unless the judge's stack is
  known to be at least that deep (`codeforces`, `icpc`): 742 bytes fewer
  in `agc077a`.
- The size check uses the profile's source limit: a warning above 75%, an
  error above the limit. The source header goes first, then half the
  indentation, only when the file would not fit otherwise.
- `I128` on a profile with `int128 = false` is an error naming the judge.

Proposed: `bits_stdcpp`, `pragmas`, memory accounting, the judge's time
and memory limits feeding `cpl bench`, and `cpl run --release --judge`
building with the profile's flags and stack.

How profiles are tested (`crates/cpl-cli/tests/judges.rs`):

- Every port is written for every profile within its limit, stamped with
  it, and without the stack switch where the judge's stack is deep.
- A million nested calls, which crash an 8 MB stack, run under each Linux
  profile's flags on the stack that judge gives (`ulimit -s`), and agree
  with the interpreter. The Windows profile is built
  with a MinGW cross compiler when there is one.
- `scripts/check.sh --full` compiles every port with every profile's flags,
  as far as the compiler here accepts them; flags it rejects are reported.

## 7.2 Things judges disagree on

Each one has a defined handling, so a solution that passes locally passes
on the judge:

- **Stack size.** Deep recursion (a DFS over a path of 2e5 vertices) crashes
  on judges with an 8 MB stack. The profile records the stack size;
  `cp budget` estimates recursion depth from ranges and warns when it can
  exceed it, and suggests the stdlib's iterative traversal. On judges that
  allow it, the emitted `main` can raise the limit (`setrlimit` on Linux) or
  run the program on a thread with a big stack; the profile says which.
- **Memory accounting.** Some judges count virtual memory, some resident.
  The MLE estimate uses the profile's method.
- **I/O.** The runtime uses its own buffered reader and writer, so speed
  never depends on `sync_with_stdio`. Interactive problems flush after
  every line (doc 1.7).
- **Output format.** Trailing spaces and the final newline follow the
  judge's checker; the default (space-separated, newline at end) is
  accepted everywhere.
- **Undefined behaviour.** The emitted C++ never relies on it: no signed
  overflow in arithmetic the checker hasn't proven safe (it uses unsigned
  wraparound or a check), no uninitialized reads. This matters because judges
  use different optimization levels.

## 7.3 The submitted file

`cp build d` writes `out/d.cpp`:

```cpp
// generated by cp 0.4.1 from d.cp (sha 3f9a...), lib snapshot 2026-11-19
// judge profile: dmoj
#include <bits/stdc++.h>
...
```

- One file, deterministic: the same source, version and profile always
  produce the same bytes.
- Readable: real names, indentation, and `// d.cp:42` markers at the start
  of each statement group, so a judge's runtime error line can be mapped
  back (`cp where 1234` prints the source line for output line 1234).
- Only the stdlib and `lib/` code actually used is included (tree shaking).
- The version stamp in the header lets the file be rebuilt exactly later.

## 7.4 Problems and samples

- `cp new d` creates `d.cp` from a template and the scratch inputs
  `i1`-`i5` (doc 4).
- `cp fetch URL` saves the samples, the limits and the problem name into
  the problem's folder. It also receives problems from the **Competitive
  Companion** browser extension, which sends them from the open problem page
  with one click.
- The time and memory limits feed the cost warnings (doc 5).

## 7.5 Submitting

- `cp build` copies the file to the clipboard by default and prints its
  size against the limit.
- `cp submit` is optional and per judge, only where the judge allows
  automated submission. It shows the verdict. Credentials stay in the OS
  keychain and are never written to project files.

## 7.6 Function-style judges

For judges that grade a function instead of stdin/stdout (LeetCode, some
IOI-style tasks with a grader), `@graded fn` marks the entry point
(decision 6.8, proposed). The emitter generates the exact signature the
judge expects, converting `List<Int>` to `std::vector<int>` and so on, and
`cp run` provides a local stand-in grader that reads the sample format.

## 7.7 How profiles are tested (proposed beyond 7.1)

- Each profile has a container with the judge's compiler version.
- CI compiles every corpus port with every profile, runs it on stored
  tests, and checks size, warnings (`-Wall -Wextra` clean) and output.
- A profile without a container is marked "untested" in `cp judges`.
