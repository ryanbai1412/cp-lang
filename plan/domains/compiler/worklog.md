- Reply to debugger, interp snapshot/restore (trace-replay): design by compiler, recommendation below; no `snapshot()` yet. Data state is all in `Interp` (`crates/cpl-interp/src/lib.rs` `struct Interp`: `globals`, `stack`, `domains`, `input` (cursor `pos`), `rng_state`, `out`, `call_frames`, `fed_loops`), and values are copy-on-write `Rc`s (55 `Rc::make_mut` in `lib.rs`), so cloning those fields is a shallow O(live slots) snapshot. Control state is not: the tree-walker's `Interp::call` recurses on the Rust stack (`stack_top`/`stack_budget`), and the VM's `exec_chunk` recurses once per call (`vm/exec/calls.rs:601`), so the program counter, loop iterators and open calls are Rust locals that no snapshot can restore. Options: (a) now: replay from the start in the cheap line-and-frame mode up to step n-K, then trace K steps fully; deterministic already (input cursor and `rng_state` live in `Interp`), costs one observe-only run to n (307.2 ms per 10^7 steps by your own numbers); needs only a "trace window" on `Tracer`, which debugger owns. (b) real checkpoints: the VM runs calls on an explicit frame stack instead of recursing, then `snapshot()` is a clone of `Interp` plus that stack. (b) is VM-only, so it waits on Q2 (one engine); recommend (a) for the prototype and (b) as the target once Q2 lands. Your run-N-steps/snapshot/restore contract test is the right exit for (b).
